# Manual

How NeoAPRS is run, set up and developed, and the rules it follows. The front page is `README.md`; the layers are in `docs/ARCHITECTURE.md`, the rules in `CONVENTIONS.md`, the roadmap in `ROADMAP.md`.

NeoAPRS is one process with one asyncio loop, the standard library first (pyserial for the serial port, Tornado for the page, pydantic for the wire only), a database actor, a systemd user unit, `scripts/check` as the one gate.

**What it does:** the daemon reads the radio, keeps every packet and the stations in its database, survives the port going away and coming back, can be run on a replayed capture without a radio, and serves a page ("The page" below): the stations on a map of the area you choose (Settings tab, Map) and in a table, the packets as they arrive, the messages as conversations, the state of the radio link, and the settings. It sends our own position ("The beacon" below) and messages to other stations, email through the APRS gateway, and answers the ones sent to us ("Messaging" below).

## Run it

NeoAPRS is a Python package with one command, `neoaprs` (and `neoaprsw`, the same without a console window, which is how Windows starts the daemon, and `neoaprs-app`, the desktop app: "The desktop app" below). From a wheel (a release, or `uv build` in a clone):

```bash
uv tool install neoaprs-0.1.0-py3-none-any.whl      # or: pip install neoaprs-0.1.0-py3-none-any.whl
neoaprs doctor                                      # what is wrong with this computer, if anything
neoaprs                                             # the daemon; open http://127.0.0.1:7303/
neoaprs service install                             # start it at login from now on
neoaprs open                                        # the page in your browser, starting NeoAPRS first if it is not running
```

In a clone (development): `uv sync --frozen` makes `.venv` with the package installed in editable mode, so `.venv/bin/neoaprs` and `.venv/bin/python -m neoaprs` are the same command:

```bash
uv sync --frozen
.venv/bin/python -m neoaprs --data data
```

`--data DIR` is the data folder (default `~/.local/share/neoaprs` on Linux (`$XDG_DATA_HOME/neoaprs`), `%LOCALAPPDATA%\NeoAPRS` on Windows, `~/Library/Application Support/NeoAPRS` on macOS; one daemon to a folder: a second one on it ends at once with exit code 2, the lock is the file `neoaprs.lock` in it; the table "Environment variables" of `CONVENTIONS.md` has `NEOAPRS_DATA_DIR`), `--port PATH` is the radio's serial port for this run only (the setting `serial/port` is not changed or
stored; a replay's pseudo-terminal, for instance), `--debug` logs more, `--version` says the version. The port is a serial port (`/dev/ttyUSB0`, `COM3`) or a KISS TCP port, `socket://host:port` (`tcp://host:port` is accepted for it): Direwolf serves KISS on `socket://127.0.0.1:8001`, the sound-card modems of UZ7HO and QtSoundModem on 8100. A TCP port has no speed, is never searched for, and nothing is sent to it that is not a KISS frame (a TCP KISS TNC has no command mode, so there is no keep-alive check); a connection that closes is a line that dropped, and it is opened again after the back-off. On Linux a Bluetooth radio or TNC that is paired with the computer is the port `bt://AA:BB:CC:DD:EE:FF` (or `bt://AA:BB:CC:DD:EE:FF/2`, with the RFCOMM channel): NeoAPRS opens the Bluetooth serial link itself, with no `rfcomm bind` and no root. It has no speed and is never searched for or opened to list it; the Port choice lists the paired devices that have a serial port, by name, and a link that drops (the radio is switched off or out of range) is opened again after the back-off like any other. On Windows the paired device's COM port is the way, on macOS its `/dev/cu.*` port (`docs/RADIOS.md`, "Bluetooth"). The control lines DTR and RTS are held low from the moment of the open, because a sound-card interface keys the transmitter on RTS. Without a port, on Linux, NeoAPRS listens to all the ports that the globs of `serial/pattern` match (by default `/dev/serial/by-id/*`, `/dev/ttyUSB*` and `/dev/ttyACM*`; a device with several names is listed once) at the same time, for as long as it takes, for the one that sends KISS frames (a TNC in KISS mode sends nothing until it hears a packet, so a quiet band means a long wait; with a profile that can be asked (see "The TNC profile") a carriage return is sent to every port after 10 s of silence, which a TNC in command mode answers and is then switched to KISS, and with any other profile, the default included, the ports are only listened to and nothing is written to them; a port another program holds is skipped, and so is a development board, known by its USB ids: ESP32, Arduino, Raspberry Pi Pico and similar boards and debug probes, whose console resets the chip when the port is opened; the log says which ports were left out and why, and a port named in `serial/port` or `--port` is never left out), remembers the one it found
as `serial/last_port` and opens that first the next time; a port that cannot be opened is followed by the search, and a line that drops is opened again after 5, 10, 20, 30 seconds. On Windows and macOS NeoAPRS listens to no port it was not told of (it could write into a GPS or into a rig interface that keys a transmitter): the radio is the port in `serial/port` or the one remembered, and the page asks the daemon for the list of the ports of the machine (`list_ports`, with a description and the USB ids of each) to pick it from; a COM port that another program has open is reported as in use by another program. In the data folder:

* `neoaprs.sqlite` is everything NeoAPRS keeps: the settings, every packet heard or sent, the messages, the message board (bulletins and group messages), our own objects, items and bulletins, the weather of the weather stations and the stations (a cache that the daemon rebuilds from the packets), in WAL mode, private to the user, migrated at the start; a copy of the file is made into `backup/` before a migration changes it.
  Packets, weather observations and stations older than 7 days are removed once a day (fixed, not a setting: the weather graphs reach back 7 days); messages and bulletins stay until you delete them.
* `neoaprs.log` is the log, rotated (20 MB, five files), with every packet as `TNC2 line -> what it is`; warnings and errors go to stderr as well, which is what `systemctl status` shows.

**How the settings apply.** The Settings tab and the Beacon tab have no Save button and no Revert: a setting is put in force as it is changed, as on a phone. A tickbox, a choice from a list, the port list, the symbol and **Pick on the map** apply at once. A field you type in (the call, the comment, the position, an interval, the path) applies when you press Enter or leave the field, never while you type, so a half-typed call or position is never beaconed; the page checks it first and says what is wrong under the field, and nothing is sent until it is right. Esc in a field puts back the value in force. Fields that belong together are sent as one change: the latitude and the longitude (under **Enter coordinates** of the Location, or a place picked with **Pick on the map**; one without the other is refused on the page), and the TCP host and TCP port (the TNC restarts once, not twice). Nothing is shown beside the field when a change applies, so that nothing on the page changes size or moves; the toast below (which floats over the page) and a screen reader's "Saved" are the confirmation. When the daemon refuses a change, the reason is under the field, what you typed stays in it, and the old value stays in force; choosing the radio as the status fills in the usual rigctld address (127.0.0.1:4532) so that the choice is valid at once, and a comment too long for the Power you set says "Shorten the comment to 36 first" on the Power. After each change a small toast, "Beacon interval changed · Undo", stays for ten seconds: **Undo** puts the old values back in one step; with several quick changes the toast is for the latest and the earlier ones just stay applied. Only a change that could cut you off asks first: turning off **Allow access from the network** on a page opened from another device. The changes go to the daemon one at a time, in the order they were made. **Beacon now** and **Send status now** (see "The page") wait while a change is being saved. The setup guide keeps its steps and its Finish button (on the first run, for a station with no call and no beacon, Finish also sets the beacon to every 30 minutes in the same save, and the last step says "Beacon every 30 min" with an (i); run again on a station that has a call, it leaves the beacon alone), and the map download stays a button (the radius and the detail apply at once, the download starts only with **Download**).

The page's forms carry no sentences under the fields (a label, a placeholder with the default, a unit, a tooltip at the most); a field that a non-developer may not understand has a small (i) that opens a few plain sentences (the TNC choice, Port, Speed, the network access, the access key and addresses, the map's Radius, the alerts, the update check). What a setting does is in this table. The settings are rows of the database, read at the start; `neoaprs db list` shows them and `neoaprs db set KEY VALUE` changes one (checked; the daemon takes it at its next start; a change made on the page is put in force at once, see "How the settings apply" below):

### The neoaprs command

`neoaprs` with no command, or `neoaprs run`, is the daemon with the flags above (`python -m neoaprs` is the same, its flags unchanged). The rest of it is the tools around the daemon, each with `--help`; `--data DIR` is the data folder everywhere (default as above, and `NEOAPRS_DATA_DIR`).

| command | what it does |
|---|---|
| `neoaprs [run] [--data DIR] [--port PATH] [--web-port N] [--debug] [--version]` | the daemon, until it is told to stop (Ctrl+C, SIGTERM) |
| `neoaprs service install\|remove\|status\|logs` | start NeoAPRS at login, the way the system does it (below); `--linger` on Linux, `-n N` for `logs` |
| `neoaprs map [--radius KM] [--maxzoom Z] [--source SRC] [--lat DEG --lon DEG] [--dry-run]` | makes the base map as the page's Download button does: the map of `map/radius_km` round the station down to `map/maxzoom` into `basemap.pmtiles`, and the world map `basemap-world.pmtiles` if there is none; fetches the `pmtiles` tool when it is missing; the flags go over the settings, `--dry-run` says the size and changes nothing |
| `neoaprs db list\|get KEY\|set KEY VALUE\|stations\|packets -n N` | looks at and changes the database: the settings (`set` is checked like the daemon checks it), the stations the daemon knows, the latest packets; the daemon may be running |
| `neoaprs open [--data DIR] [--no-browser] [--timeout SEC]` | opens the page in the default browser; when no daemon holds the data folder (the instance lock) it starts one first, detached: on Windows `neoaprsw.exe run` with no console window, elsewhere a child in a session of its own whose output goes to `neoaprs.log`. It waits for the log line `web page at` and for the page to answer, so the port can be any of the ten from `web/port`; prints the address; `--no-browser` only starts and prints. On failure it says why (on Windows from `neoaprsw.exe` in a message box) and exits 1. The Start menu's "NeoAPRS" runs `neoaprsw.exe open` |
| `neoaprs stop [--data DIR] [--timeout SEC]` | ends the daemon that holds the data folder, cleanly (the end of SIGTERM: `NeoAPRS ended` in the log), on every system: it writes the file `neoaprs.stop` into the data folder, which the daemon looks for once a second (`neoaprs/stopfile.py`), deletes and ends on, and waits until the instance lock is free. Exit 0 when it ended or none was running, 1 after `--timeout` (30 s). No port, no key: whoever can write to the data folder (private to the user) could kill the process as well. A service manager that restarts it starts it again: use `systemctl --user stop neoaprs` there. The Start menu's "Stop NeoAPRS" and the uninstaller run it |
| `neoaprs replay [FILE] [--interval S] [--loop] [--port P]` | plays a capture as a KISS TNC on a TCP port of the loopback and prints `socket://127.0.0.1:PORT`, to run the daemon without a radio on any system (below); with no FILE it plays the sample capture inside the package, `neoaprs/samples/thd7.kiss` (three minutes of a TH-D7, a copy of `tests/fixtures/kiss/thd7-2026-10-21.bin`); `--pty` plays on a pseudo-terminal instead (Linux, macOS) |
| `neoaprs capture OUT [--port PORT] [--seconds N] [--baud N] [--force]` | records the radio's serial port into a file byte for byte and shows its KISS frames, to make test fixtures or to find the radio's port (without `--port` it probes the usual USB serial names on Linux) |
| `neoaprs app [--data DIR] [--tray] [--quit] [--timeout SEC]` | the desktop app ("The desktop app" below; needs `neoaprs[app]`): the page in a window and a tray icon, attached to the daemon of the data folder or with one of its own; `--tray` starts with the window hidden, `--quit` ends the app that is running |
| `neoaprs doctor` | the checklist below |

**The doctor.** `neoaprs doctor` prints one line for each thing NeoAPRS needs, marked `ok`, `warn` or `FAIL`, and under each line that is not ok the command or step that cures it; it changes nothing (the database is opened for reading, the ports are listed and not opened) and its exit code is 1 when something failed, 0 otherwise. It checks: the Python (3.13 or newer); the data folder (made yet, writable); the database (readable, its version against the one this NeoAPRS uses: a file of a newer NeoAPRS fails, an older one is migrated at the next start); the call (`station/call`, "set your call on the page" while it is empty or cannot transmit); the serial ports the system lists, with the description and the USB `VID:PID` of each, which is also what to paste into a bug report; on Linux, whether you are in the group that owns the serial devices (`dialout`, `uucp` on Arch) and whether **brltty** or **ModemManager** are installed, which take USB serial adapters (brltty makes a CH340, CP210x or FTDI port vanish as it is plugged in, ModemManager probes new ports as modems), with the way to remove or stop them; on Linux with KDE, whether Firefox is a Flatpak whose web pop-ups can go missing (the two `flatpak override` commands, read and never run: "Messaging", "Alerts in the page"); whether a daemon holds the data folder (the instance lock) and where its page is and whether it answers; the base map files and their sizes; and whether the service is set up.

### The TNC profile

`tnc/profile` says what is written to the TNC and how it is reached. The TNC group of the Settings tab opens with the **radio status**: the state as a coloured word (connected, waiting, silent...), one plain line ("Last packet 2 min ago" (the pill says connected and Port below names the port); "Searching for the radio…" with the ports it listens to behind "Ports"; "Not connected: the reason"; for a silent radio since when it said nothing; the packets and bytes counted are the line's hover title), the problem when the line does not already say it, and **Reconnect**, which opens the line again. Under it "Terminal", closed until it is opened, shows the latest 100 lines of what the TNC saw and did, in monospace and in the browser's time (the daemon writes them in UTC), following the end unless it was scrolled up. The group then shows the profile first, as "Radio type", and the fields that follow it: for a TCP profile the host and the port; for a serial one the **Port** (find automatically, a port from the list, or one typed; the port found last is told beside it, not a field), the **Speed** in baud. Which ports the search looks at and leaves alone (`serial/pattern`, `serial/skip`) are not on the page: the defaults suit nearly everyone, and `neoaprs db set` changes them. The profile is the one place that knows a device's words (`neoaprs/tncprofile.py`, with the source of each string in a comment); a device that needs nothing is sent nothing.

| profile | for | entry (the wait after each step) | leave | asked if it is there |
|---|---|---|---|---|
| `kiss` (default) | Mobilinkd TNC3 and TNC4 (USB or Bluetooth serial), NinoTNC (set `serial/baud` to 57600), TNC-Pi, TNC-X, the Kenwood TH-D74 and TH-D75 with KISS switched on at the radio (`[F]` then `[LIST]` on the D75), any TNC that is in KISS when it is switched on | none | none | no |
| `kiss-tcp` | Direwolf (8001), UZ7HO SoundModem and QtSoundModem (8100): a program that serves KISS over TCP | none | none | no |
| `kenwood-tnc2` | Kenwood TH-D7, TM-D700, TS-2000; TAPR TNC-2 and the MFJ-1270B/1274/1278 and PacComm clones | `\rKISS ON\rRESTART\r` (3 s) | `C0 FF C0` | yes |
| `kenwood-d710` | Kenwood TM-D710A/E/G/GA/GE, TH-D72A/E | `TC 1` (1 s), `TN 2,0` (3 s), `HBAUD 1200` (1 s), `KISS ON` (1 s), `RESTART` (1 s), each ended by a carriage return | `C0 FF C0` | yes, the check enters again with the whole sequence |
| `kantronics` | Kantronics KPC-3+, KPC-3, KAM | `\rINTFACE KISS\rRESET\r` (3 s) | `C0 FF C0` | yes |

* **A TNC that is not asked** (`kiss`, `kiss-tcp`): nothing is written to it but KISS frames. There is no entry, no keep-alive check, no carriage return after silence or in the search for the port, and no `silent` state: the open serial line or TCP connection is all the Tnc can know of the radio (a TCP connection that closes, or a serial device that goes away, is a line that dropped and is opened again after the back-off). A TNC in command mode that sends text is told in the radio status of the Settings tab; it is not answered. The Kenwood TH-D74 and TH-D75 have no command mode at all and cannot be asked; put them in KISS at the radio.
* **The wait after the last step** is the settle time: what the TNC says meanwhile is thrown away and no frame is sent. The `kenwood-tnc2` sequence is the one the Kenwood TNC-2 takes. The `kenwood-d710` sequence is the one of the tmd710_tncsetup project (Debian); what `TC 0` and `TC 1` mean is not documented by Kenwood, so the sequence is copied as it is, and the check of this profile has not been tried on a radio. The `kantronics` entry is from the KPC-3+ manual; a reset has been reported to change the host speed on some units.
* **KISS over TCP** connects to `tcp/host` and `tcp/port` (or to the address in `serial/port`, which is then used as it stands), is never searched for and has no speed. A sound-card interface (a Digirig, a SignaLink) is not a TNC: run Direwolf or a sound-card modem on it and use `kiss-tcp`; opening the interface's serial port as a KISS TNC would key the transmitter on RTS.
* **A socket address in `serial/port`** works with every profile; the profile then says what is written to the device behind it.
* The profile list is not a promise that a device works: the strings are from the manufacturers' manuals and from users' reports, and `docs/RADIOS.md` marks which is which.

### The TNC keep-alive

A radio that is switched off leaves the USB adapter and its port in place, a radio that is power-cycled comes back with its TNC in command mode, and a TNC in KISS mode says nothing until it hears a packet, so a quiet line proves nothing: the radio's absence has to be asked for. While the port is open and the profile can be asked, the Tnc counts the time since anything at all arrived (a damaged frame or noise counts). After a quiet `check_sec` (60 seconds) it makes a **check**: the profile's exit (`C0 FF C0`), half a second, a bare carriage return, and then the profile's entry (`KISS ON` and `RESTART` for the Kenwood TNC-2, the whole sequence for the TM-D710) with its settling time. A TH-D7 that is on answers with text (`cmd:`) within about a second; any byte in answer means the radio is there, the state stays `connected` and the clock starts again from the latest byte. The check costs a few seconds of reception, which is why it runs only after a quiet minute and never while packets flow. **A line that has just been opened** (the daemon starts, or the line dropped and was opened again) has not shown yet that the radio is there, because the USB adapter is there with the radio switched off: for a profile that can be asked the Tnc makes this same check at once, and until a byte arrives (a packet, or the answer to the check) it is `connected` but not `usable`, with the reason "the TNC is checking that the radio is there": the beacon, the status, the messages, the acks and the answers to queries wait exactly as they wait while the radio is silent. A byte heard before the check runs confirms the line and the check is skipped, and so does a port that the search chose, which has just been heard from. No byte within the check's answer time makes the radio `silent` and the probing starts at once. The profiles that cannot be asked (`kiss`, `kiss-tcp`) are usable as soon as the line is open. Nothing is sent while a check is under way or settles (`Tnc.usable` is False), so no frame is ever typed into a TNC that is in command mode. The check, the silent state and the probes exist only for a profile that can be asked (`kenwood-tnc2`, `kenwood-d710`, `kantronics`); the `kiss` and `kiss-tcp` profiles never have them. A new `check_sec` counts at once, with no restart.

**A silent radio.** When no byte at all comes within 2 seconds (`answer_sec`) of the carriage return and `KISS ON`, the state is `silent` (`Source.State.SILENT`): the line is open while the radio does not answer. The Tnc sends nothing while it is silent (a frame is refused with "the radio is silent"): the beacon that is due waits for the radio (told once in the log; see "The beacon"), the status report and the answers to queries are not sent, the attempts of a message wait and none is used up (as when the line is away), and `beacon_now` and `send_message` are refused with the reason "the radio is silent". The topic `tnc` has `state` `silent` and `silent_since`, the time of the last byte received (null otherwise), and `describe` says `silent since 18:43 (17 min)` in UTC. A radio switched on again is found within a minute: while the Tnc is silent it **probes** every 30 seconds (`probe_sec`), the same sequence as a check, and every 5th probe also closes the port and opens it again (a USB adapter that dropped; the radio stays silent across it). The first byte that arrives, whatever it is, ends the silence cleanly: the Tnc is `connected`, the allowance to enter KISS (once for every answer: a fresh open, each return from silence, each check or probe) is given back, the mode detector starts over, and KISS is entered (the profile's entry) unless the bytes are a KISS frame already; the Tnc is not `usable` until the settling time after that has passed, and a beacon that fell due in the night goes out then, as a KISS frame, never into a TNC in command mode.

**The log.** A check that finds the radio, each probe and each KISS entry made by a check or a probe are DEBUG only. The log has the line `the radio is silent: nothing heard since 18:43 UTC, no answer to a check; probing every 30 s` once at WARNING when the silence begins, and `the radio answers again after 17 min; entering KISS` once at INFO when it ends; a KISS entry on a fresh open stays INFO. The topic `tnc` counts in `stats`: `keepalive_checks`, `watchdog_probes` and `port_reopens`, and has `last_watchdog_action` (`check`, `probe`, `reopen` or empty) with `last_watchdog_at`; the page shows the packet and byte counts as the hover title of the radio status. The check at a fresh open is DEBUG when the radio answers, and the silence it may find is the same one warning; a fresh open sends no carriage return of its own after a quiet spell, the check at the open does that.

### The beacon

With `beacon/interval_min` above 0 (the page offers Off, every 15, 30 and 60 minutes) the daemon sends our position: the first beacon 30 seconds after it starts (the radio and the TNC settle first), then one every interval, counted from the latest beacon, however it was sent. A restart does not send another: the time of each beacon is kept in the row `beacon/last_sent_at` of the database (state of the daemon, not a setting: the Settings tab does not list it), and a daemon that starts less than an interval after it sends its first beacon at that time, an interval after the one before, not 30 seconds after the start; with no row, or one that is older, it is 30 seconds as above; **a beacon that falls due while the Tnc is not connected or the radio is silent (switched off at night) is not skipped**: it stays due, the log says once per outage `the beacon is due and the radio is silent: it goes out when the radio is back`, and the first second the radio is usable again it goes out, one beacon however many intervals went by, and the next is an interval after it; a frame the Tnc refuses (it is settling for a few seconds after entering KISS, or the write failed) is tried again 5 seconds later, six refusals in all, and then that interval is skipped (the next is the first interval boundary after now); an outage shorter than the interval sends nothing extra; "Beacon now" and a changed interval count from the kept time. It is an AX.25 UI frame from `station/call` to the tocall `APZNEO` by way of `beacon/path`, and its information field is `=` (a station that takes messages), the position of `station/lat` and `station/lon` rounded to the hundredth of a minute, the symbol (`station/symbol_table`, `station/symbol_code`) and `station/comment`: with the defaults it is
`OH2GBA>APZNEO,WIDE1-1,WIDE2-1:=6010.20N/02456.40E-NeoAPRS`. The form of the position is NeoAPRS's choice, not a setting: always the plain uncompressed one, which every receiver reads, with no DAO. (Rows `beacon/compressed` and `beacon/dao` of an older database are ignored and may stay.)
**PHG.** With `beacon/power_w` set the beacon carries the PHG extension `PHGphgd` right after the symbol code, where p is the square root of the power in watts, h the base-2 logarithm of the antenna height in tens of feet, g the gain in dB and d the directivity (0 omni, 1 NE, 2 E, 3 SE, 4 S, 5 SW, 6 W, 7 NW, 8 N, the specification's order), p and h rounded and held to 0 to 9 (2 W, 3 m, 2 dB, omni is `PHG1020`; 25 W, 6 m, 3 dB, east `PHG5132`, the specification's example; with no power set no PHG is sent, and the Beacon tab asks for the antenna's height, gain and direction only once there is a power). The comment may be 43 characters, **36 when the PHG is sent**, and the beacon is refused (the log says why) when it is longer, as a save of the settings is. The Beacon tab's preview shows what is sent.
**The tocall.** `APZNEO` is in the experimental range (`APZ...`) of the destination calls, and it is a constant of the program (`TOCALL` in `neoaprs/__init__.py`), not a setting: every frame we send has it, the beacon, the status, the messages and their acks, the answers to queries, the objects and the bulletins, and a `beacon/destination` row that an older database holds is ignored. A tocall of our own is registered by opening an issue at <https://github.com/aprsorg/aprs-deviceid>; it would then replace the constant. Saving the settings with another interval takes effect at once (0 stops the timer); the frame is made when it is sent, from the settings then.

By hand: the Beacon group of the Beacon tab starts with a row "Last beacon: 2 min ago" (the full time on hover) with **Beacon now**, a primary button beside it that asks twice ("Really send?"), is disabled while the TNC is not connected or while a change of the settings below is being saved (what is sent is what is in force), and the Status group has a **Send status now** beside the status line (below); the next beacon of the timer is then an interval later. A beacon we send is in the packet log and in the Packets tab as a packet with direction `out`, and our own row on the map is the settings' (position, symbol and comment), never what a packet says; a packet with our own call that is heard back (the TNC may echo what it sends, a digipeater repeats it) only updates the time we were last heard.
**The status.** The status report (`>`, the day, hour and minute in UTC and a `z`, the specification's time stamp `DDHHMMz`, then the text; an AX.25 UI frame from `station/call` to the tocall by way of `beacon/path`) is sent by `services/rigstatus.py` by one rule, whether the text comes from the radio or from the settings. **Where it comes from** is `status/source`: `off`, `text` or `rig`; the Beacon tab's Status group is one choice of the three (*off*, *a text of my own*, *the frequency from my radio (rigctld)*) and then only the fields that choice needs: for a text, **Text** (`station/status`) and **Every**; for the radio, **Rigctld**, **Text** (`status/template`, with `{freq}` and `{mode}`) and **Every**; for *off* nothing more. Empty, `status/source` follows the other settings as the daemon works it out: `rig` while `status/rigctld` is set, else `text` while `station/status` is not empty, else `off`, so an installation from before the choice does what it did. **From the radio:** with the source `rig` (`host:port` of a Hamlib rigctld) the daemon connects to it every 30 seconds, a fresh short connection each time, asks `f` (the frequency in Hz) and `m` (the mode and the passband), and fills in `status/template`: with `14074000` and `USB`, `QRV {freq} {mode}` gives `QRV 14.074 MHz USB`, and the frame, at 12:00 UTC on the 21st, is
`OH2GBA>APZNEO,WIDE1-1,WIDE2-1:>211200zQRV 14.074 MHz USB`.
**The rule:** a status goes out when `status/interval_min` (default 30) has passed since the last one sent, or none was sent since the daemon started, **and** what it says has changed since that one: the frequency to the kHz or the mode for a radio, the text for the static status. So nothing goes inside the interval however the dial moves, nothing when it is the same (a long quiet band does not repeat itself every half hour), and the first status goes out at the first poll after the start. **A restart does not resend it:** the time and the text of the last status sent are kept in the rows `status/last_sent_at` and `status/last_text`, and read at the start, so a daemon started inside the interval sends nothing, and one started after it sends a status only when the frequency and mode (or the static text) differ from the kept text; with no rows the first status goes out at the first poll. **The radio off:** an `RPRT -n` answer from rigctld (a radio that is switched off), a refused connection or no answer within 5 seconds means the radio is off or rigctld is away: nothing is sent and the log says so once, when it begins (`rigctld at 127.0.0.1:4532: connection refused: no status while it is away`) and once when the radio answers again, not at every poll. **Send status now:** the button of the same name at the top of the Status group of the Beacon tab, beside the status line (there only while the status is not off; it asks twice, like Beacon now, and acts on the saved settings), sends the status at once with the command `status_now`, inside the interval and although nothing changed, by the same checks: nothing is sent while the call is not set (the interlock), the text is at most 55 characters with the time, the TNC must be connected; with the radio it reads the frequency first and says when rigctld is away; an empty text, the status off or the settings that make no frame are answered with an `error` that says why. The interval counts from it. **The text status:** with the source `text` the text of `station/status` follows the same rule, so it is sent once at the start (when the TNC is connected; it waits otherwise) and again only when it was edited and the interval has passed; an empty text sends nothing. The text is printable ASCII without `|` and `~` (a TNC takes them for commands), at most 55 characters (the specification allows 62 only for a status without a time; ours always has one) and is checked when it is saved, the template with its widest fill; the frame is checked again when it is made; a report the TNC would not take is told once and tried again at the next poll. The last text sent is the answer to the query `?APRSS` (see "Queries") and the "Status" line of the Beacon tab, which also says whether rigctld answers; the `status` message of the wire has it as `station_status` and `rig_state` (`on`, `off`, or `unused` while the status does not come from a radio).

A first transmission on the air is not tested by the suite (it never opens the radio): check it live, by "Beacon now" and then looking for OH2GBA on aprs.fi or on another station's screen, before leaving a timer on.

### The digipeater

Off unless `digi/enabled` is `true` (Settings tab, group Digipeater, with an (i)): a fill-in digipeater for a spot with poor coverage, where nearby stations cannot reach a digipeater of their own. There is nothing else to set. When it is on, `services/digipeater.py` sends a packet it heard on the radio again, once, when the first digipeater of the packet's path that is not yet marked as used is

* `WIDE1-1`: our call, marked as used, takes its place, so `OH2XYZ>APRS,WIDE1-1,WIDE2-1` goes out as `OH2XYZ>APRS,OH2GBA*,WIDE2-1`;
* our own call with our SSID (a station routing through us on purpose): that hop is marked as used where it stands.

Nothing else is repeated: not a path whose first unused hop is anything else (`WIDE2-1`, `WIDE2-2` and the like are for the digipeaters on a high site), not a packet from our own call or one that already shows our call as used, not a duplicate (the same source, destination and information field heard or sent by us in the last 30 seconds, whatever the path), and not a packet from the internet (third-party traffic, `}`, or a path with `TCPIP` or `TCPXX`; `NOGATE` and `RFONLY` ask iGates only and are repeated). The frame is the one that was heard with only the path changed. It goes through the same checks as every transmission: nothing at all while no call is set or the radio is not usable. A fill-in is of use only at once, so it does not wait for the 10 seconds between our scheduled frames; at most 4 digipeated frames go out in any 10 seconds, and the rest are dropped. Each one is a line at INFO in the log (`digipeated OH2XYZ>APRS: the path WIDE1-1,WIDE2-1 is sent as OH2GBA*,WIDE2-1`), is in the packet log as a packet with direction `out`, and is counted: the topic `tnc` has `stats.digipeated` and the radio status of the Settings tab says "digipeated N" while the digipeater is on and N is more than 0 (the count is also in its hover title).

### Messaging

The Messages tab of the page (the commands `send_message`, `message_retry`, `message_cancel`, `message_delete` and `conversation_delete` of `PROTOCOL.md`; the messages to bulletins and groups are the board's, below) sends APRS text messages to other stations and shows the ones sent to us, as conversations, one for each other call. Every message is a row of the table `message`, so a restart goes on where the daemon stopped.

**Sending.** The addressee is a call with an optional SSID (written in upper case); our own call (with its SSID: the base call of ours with an SSID is another station) is refused. The text is at most 67 characters of printable ASCII (the specification's text: a letter with an accent is refused, the radios of the stations that read it would show it wrongly) and has no `|`, `~`, `{` or control character and does not begin like an ack or a reject (`ack12`); a refusal names the reason. The message is given the next message id (two characters, `01` to `99`, then `A0` to `ZZ`, `0A` to `9Z` and `00`: 1296 in all, one after the other, going round and skipping the ids of messages still being sent) and goes out at once as an AX.25 UI frame from `station/call` to `beacon/destination` by way of the station's path (below), whose information field is `:`, the addressee padded to nine characters, `:`, the text, `{`, the id and `}`: the braces say that we know reply-acks (below), and when the station has sent us a message with a reply-ack number that its own ack has not yet reached it with, the id of the latest of them follows the brace. With the defaults our first message, "Hello Pekka" to OH2RDG, is
`OH2GBA>APZNEO,WIDE1-1,WIDE2-1::OH2RDG   :Hello Pekka{01}`.
A message to a bulletin or a group (`BLN0`..`BLNZ`, `BLN3HAMS`, `ALL`, `CQ`, `QST`, `NWS-xxxxx`, `SKY`, `CWA`) goes out once, without an id (`OH2GBA>APZNEO,WIDE1-1,WIDE2-1::BLN1     :Road closed`), is never retried and is kept as `unconfirmed` with one attempt.

**The attempts.** The same frame is sent again until the addressee answers, 4 times in all (the code decides it: there is no setting and no field on the page), and a message to the email gateway `EMAIL-2` 2 times, since its acks rarely reach us. The waits double: the 4 attempts are made 0, 30, 60 and 120 seconds after the first, the 2 to the gateway at 0 and 30. The answer to the last attempt is waited for 240 seconds, then the message has `failed`, unless it was given only 1 or 2 attempts (the gateway's, a bulletin's): then it is `unconfirmed` (below). The number is the message's own: it is kept with it (`attempts_max`, in the database and on the wire) from the moment it is sent, so a message sent by an earlier version, which let the operator choose 1 to 10 (the setting `messages/attempts` and a count for each station, both gone: what they left in the database is ignored and harmless), goes on with the number it has, up to 10 attempts at 0, 30, 60, 120, 240, 480, 960, 1920, 2880 and 3840 seconds (no wait is longer than 960 seconds), and Retry keeps it. An ack from the addressee that quotes our id makes it `acked`, a reject `rejected`; either ends the attempts, and one that comes late still settles a message that has failed, is unconfirmed or was cancelled. On the page Cancel stops a message that is being sent (`cancelled`) and Retry sends a failed, unconfirmed, rejected or cancelled one again from the first attempt, with the same id. While the TNC is not connected an attempt that is due waits for it: none is used up, the waits that were running are moved on by the time the radio was away, and the log says so once; a message written then is kept and its first attempt goes out when the TNC is back. After a restart the schedule goes on from the latest attempt that was made.

**The pace.** Our attempts to send, of any messages, go out one at a time, at least 10 seconds apart (`SPACING_SEC` of `services/pace.py`). The first message goes at once; messages written together, such as one text to several stations, wait their turn in the order they were written, with their state `sending` and no attempt used, and each follows 10 seconds after the one before. The retries of different messages keep the pause too. Acks and the answers to queries are not held back.

**Receiving.** A message is for us when its addressee is `station/call` with its SSID, exactly (no SSID and `-0` are the same; with OH2GBA-7, a message to OH2GBA-7 is ours, those to OH2GBA and to OH2GBA-9 are other stations'). A text that is a query (`?APRSP` and the others of "Queries" below), or the definition of the channels of a telemetry station (it begins `PARM.`, `UNIT.`, `EQNS.` or `BITS.`; to us or to anyone), is neither kept nor acked, whatever id it carries: the packet log has it. It is kept (direction `in`, state `received`, from the packet's source) and, when it carries an id, answered at once with an ack from our call to `beacon/destination` by way of the sender's path (below): for message 12 from OH2RDG-7, with the default path, it is
`OH2GBA>APZNEO,WIDE1-1,WIDE2-1::OH2RDG-7 :ack12`.
A text that reads as an ack or a reject (`ack12`, `rej12`) is one only when it quotes the id of a message of ours to that station (in any state: the second of two acks changes nothing); otherwise it is the words of a person ("rejoin", "ackbar"), kept as a message without an id and not acked.
One ack goes out for each burst of copies of a message: the first copy that is heard is acked at once, and a further copy of the same message (the same sender, id and text, which is also what the 30 minutes below count by; a digipeater's copy, an iGate's copy of what the internet said) is acked again only when it arrives more than 10 seconds after our last ack of that message, which is a sender that did not hear us and tries again. The copies that come sooner are not acked (the log says so at debug level), so three copies in six seconds cost one ack on the air. The same id and text from the same station within 30 minutes is a repeat and is kept once, however often it is acked; after 31 minutes it is a new message and is acked at once, and so is a new text with an id that was used (a sender that began its numbering again). The time of the last ack is held in memory, like the rest of this bookkeeping, so after a restart the first copy is acked again. A message without an id is kept and not acked; a repeat of it (the same sender, addressee and text, which is what two digipeaters' copies of an auto-reply look like) within the same 30 minutes is not kept again, as with an overheard message, and the same text after 31 minutes is a new message.

**Reply-acks.** An ack that has to cross several hops is the likeliest frame to be lost, so (WB4APR's addendum of 1999, `aprs.org/aprs11/replyacks.txt`) a message may carry an ack for the other station's latest message in its own number: `{MM}AA`, where `MM` is its id and `AA` the id of a message of the other station; `{MM}` alone says that the sender knows the form. Every message we send has the number in that form, and the normal ack frames go out too, the reply-ack is extra. With the defaults, a message 05 from OH2RDG that said `{05}` and our answer to it, message 01:
`OH2GBA>APZNEO,WIDE1-1,WIDE2-1::OH2RDG   :ack05` and `OH2GBA>APZNEO,WIDE1-1,WIDE2-1::OH2RDG   :Moikka{01}05`.
Every attempt of a message to a station is made with the id of the latest message that station sent us with such a number, until the station acks or rejects a message of ours (a retry keeps its id and carries the latest `AA`); a message from a station that sent it as `{MM`, without the closing brace, is owed nothing. A message that comes as `{MM}AA` is acked with a copy of its number, `OH2GBA>APZNEO,WIDE1-1,WIDE2-1::OH2RDG   :ack05}01`, and its `AA` settles our message with that id to that station as an ack does (the plain ack that follows settles nothing more); an ack of the form `ackMM}AA` acks our message `MM`. The `AA` is not part of the text that is kept, so a repeat with another `AA` is a repeat.

**The delivery chain.** A copy of one of our own messages that the radio hears again (the packet from our call with the same addressee, id and text; also one an iGate gated back as a third-party packet) is no new message: `services/delivery.py` links it to the message and to the attempt it belongs to, the latest attempt sent before it was heard. Each attempt keeps when it was sent and the digipeaters it went by (the table `message_attempt`), and each hop of that path that a copy was heard with its has-been-repeated bit set (the table `message_hop`: the position, the call that did it, which is the one heard when the path had an alias such as `WIDE1-1`, when, and whether it was a third-party copy; position 0 is such a copy whose own path names no hop, with the iGate's call). A hop used implies the hops before it, so `OH2RCH-2,OH2RDG*` shows both. Acks and copies of other messages are not linked. Both tables go with the message when it or its conversation is deleted, and a retry starts a new chain. The row of the topic `messages` has `attempts_detail`, an entry for each attempt with its hops, and a hop that is heard is a `set` of the row. On the page the thread shows under a message of ours the chain of its latest attempt, `you → OH2RCH-2 → OH2RDG → OH2CUB-7`: a hop heard is green with a check, one not heard grey with a `?` (its title says "beyond what this station can hear" when that digipeater was never heard direct), one seen only in a copy gated back blue with `internet`, and the recipient is green on the ack, red on failure and grey while it waits. Only the latest attempt's chain is shown: the line above it already says which attempt it is ("attempt 3 of 4").

**Alerts.** When a message to us arrives, `services/alerts.py` runs the shell line `messages/alert_command` (when `messages/alert` is on, the default), by `asyncio.create_subprocess_shell`, with these in its environment: `NEOAPRS_FROM` (the sender's call), `NEOAPRS_TEXT` (the text), `NEOAPRS_AT` (when it was heard, ISO 8601 in UTC, `2026-10-21T12:00:00Z`) and `NEOAPRS_MSG_ID` (the id the sender gave it; empty when it had none). The text is in the environment and not in the command line, so what a stranger wrote is never read as shell; quote the variables in your own command. The default is `(notify-send -- "APRS message from $NEOAPRS_FROM" "$NEOAPRS_TEXT" 2>/dev/null || kdialog --title "APRS message from $NEOAPRS_FROM" --passivepopup "$NEOAPRS_TEXT" 10); paplay /usr/share/sounds/freedesktop/stereo/message-new-instant.oga` (a notification and a sound). The alert runs for the **first copy** of a message only (not for a repeat of a retry or another digipeater's copy), and never for a bulletin or a group message, an ack, a reject, a query we answer (`?APRSP` and the others), a message we only overheard, or one of our own. The command gets 20 seconds and is then killed with everything it started; its output is in the log at DEBUG; a command that fails (it cannot start, exits with a status other than 0, runs out of time) is a warning in the log once an hour and a line at DEBUG otherwise, and never touches the daemon. Its environment is not the daemon's: only the names a program needs to find the desktop (`PATH`, `HOME`, `DISPLAY`, `WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_*` ...), the `NEOAPRS_*` variables above and nothing else (`neoaprs/childenv.py`); `neoaprs/cli/neoaprs.service` sets `DBUS_SESSION_BUS_ADDRESS=unix:path=%t/bus` so that `notify-send` finds the desktop from a user service. At most 5 alerts run at once; more are dropped. **On Windows** the command is a PowerShell script (`powershell.exe`, run from a thread as an encoded script, so nothing of the line is quoted and the text is never in it): read the variables as `$env:NEOAPRS_FROM` and `$env:NEOAPRS_TEXT`; a step that fails ends the script with status 1 (`$ErrorActionPreference='Stop'`), `exit N` gives its own status, and a run out of time is killed with everything it started (`taskkill /T /F`). The default there is a PowerShell toast with the sender and the text, and the system's sound; it is not tried on a real desktop by the tests. **The Test button.** Right of the `messages/alert_command` field (Command) in the Settings tab, in the group Notifications, a Test button sends `alert_test`: the daemon runs the command as it is saved, exactly as for a real message (the same shell, the same environment, the same 20 seconds) with `NEOAPRS_FROM` set to `NEOAPRS`, `NEOAPRS_TEXT` to `This is a test of the NeoAPRS alert`, `NEOAPRS_AT` to now and `NEOAPRS_MSG_ID` empty, whatever `messages/alert` says (a test is explicit), waits for it and answers `alert_result{ok, text}`: `ran` when it worked, else the exit code and the first line of stderr (`exit code 3: no display`), or that it could not start or was killed. An empty command is an `error` (`no alert command`). The page shows the answer under the field (green when it worked, red when not) until the next edit; the button waits while a test runs, and is disabled, with the title "Save first", while the field differs from the saved command.

**Alerts in the page.** The alert command runs on the computer the daemon runs on, which is not where you are when NeoAPRS is a service on a Raspberry Pi and the page is open on a laptop or a phone. So the page alerts by itself, in the browser, for the same messages as the command (a message to us, the first copy; not a bulletin, a message we only overheard or one of our own), once for each message that arrives while the page is open, in a background tab too (what the page loaded with, and what it is told again after a reconnect, is not new). Everything about being alerted is in one group of the Settings tab, **Notifications**, in two parts: **On the NeoAPRS computer** is the daemon's own alert (the settings `messages/alert`, labelled Alert, and `messages/alert_command`, labelled Command, with its Test button: "The Test button" above), and **In this browser** is the page's own alert, described here.

**In this browser** has one choice, **Alert for a new message**, kept in this browser (`localStorage`), not on the daemon, so each device decides:

| choice | what a new message does |
|---|---|
| **off** | nothing |
| **sound** | a short chime (made by the page, no sound file), and, while the page is hidden or not in focus, the alert of the browser tab: the tab's title alternates between "✉ OH2DPN" and the usual one and the icon has a dot, until the page is seen again (the count of messages not seen stays in the title) |
| **sound and pop-up** | the chime and a pop-up (a notification of the browser), "APRS message from OH2DPN" with the text; a click on it brings the page to the front and opens that conversation. Where no pop-up is shown after all (the permission was not given, the browser refuses or could not show one) the tab alert takes its place |
| **pop-up only** | the pop-up, without the chime, and the tab alert where it cannot be shown |

A page opened from another device starts at **sound and pop-up** where the browser can show pop-ups, else at **sound**; a page on the computer itself (`localhost`, `127.0.0.1` or `[::1]`, and the desktop app), where the alert command already notifies, starts at **off**, so that nothing alerts twice. The two choices with a pop-up are disabled, with the reason as their hover title, where the browser cannot show one: "Pop-ups are off in this browser for this address" and "Pop-ups are blocked for this page in the browser". Where the reason is the address (a page opened over plain http from another computer), **Enable pop-ups…** stands beside the choice and opens the steps for the browser in use, inside the page ("Pop-ups need a secure context" below). Choosing one is the click that asks the browser for the permission (the page never asks by itself, and not when it loads); when it is refused the choice goes back to **sound** and the words "pop-ups refused: sound only" stand beside it. Next to the choice the words "pop-ups not allowed yet" or "pop-ups blocked" say that a pop-up is chosen but the permission is not there. A browser lets a page make a sound only after you have clicked or pressed a key in it, so the chime is silent until then and the tab alert is all there is. A page that kept the three switches of an earlier version (Web alert, Sound, Notifications) turns them into the one choice the first time it loads and drops them.

The group has a test beside what it tests, each of which works whatever the choice is and says for a few seconds what happened:

| button | what it does | words after it |
|---|---|---|
| **Test sound** | plays the chime now | `played`; `sound locked: click the page once` when the browser will not let the audio run yet |
| **Test pop-up** | shows a pop-up now, "APRS message from NEOAPRS" (it asks for the permission first if the browser has not been asked); where none can be shown it flashes the browser tab for a few seconds instead | `pop-up sent`; `pop-up blocked` when the permission is refused or the browser will not show it; `pop-ups are off for this address` when the address does not allow pop-ups, with **Enable pop-ups…** beside it |
| **Test** (on the NeoAPRS computer) | runs the alert command as it is saved | the command's result, under its field |

**Pop-ups do not appear?** When Test pop-up says `pop-up sent` and nothing shows, the browser has handed the pop-up on and something outside the page holds it back. Look at, in this order: the site's permission in the browser (the padlock of the address bar: notifications must be Allow); the desktop's do-not-disturb or focus mode; and, for **Firefox installed as a Flatpak on KDE Plasma**, the desktop portal: Firefox hands its pop-ups to it, and the KDE portal accepts them and never shows them (seen with Plasma 6.3 and xdg-desktop-portal-kde 6.3.5). The cure is to let Firefox talk to the notification service itself, and to tell it not to use the portal, then restart Firefox:

```
flatpak override --user --talk-name=org.freedesktop.Notifications org.mozilla.firefox
flatpak override --user --env=NOTIFY_IGNORE_PORTAL=1 org.mozilla.firefox
```

`neoaprs doctor` checks this and prints the two commands when the overrides are missing (it only reads them). To undo it: `flatpak override --user --no-talk-name=org.freedesktop.Notifications org.mozilla.firefox` and `flatpak override --user --unset-env=NOTIFY_IGNORE_PORTAL org.mozilla.firefox`. A browser from the system's own packages does not go through the portal.

*Pop-ups need a secure context*: `localhost`, HTTPS, or an address you have told the browser to treat as one. A page opened at `http://<pi-address>:7303` is not one, so tell the browser; **Enable pop-ups…** in the Settings tab (Notifications, In this browser) shows these steps in the page, for the browser in use, with the host or the address ready to copy:

1. **Firefox** (a computer): open a new tab, type `about:config`, press Enter and click "Accept the Risk and Continue"; search for `dom.securecontext.allowlist`; if it is not there choose "String", click "+", put in the host name or address alone, without the port (`neoaprs-pi.local` or `192.168.1.20`) and click the tick (if it has text already, add a comma and the host at the end); come back to the page and reload it. If the pop-up still does not show and Firefox is a Flatpak on KDE, run the two `flatpak override` commands above (the panel has them in a fold, "If the pop-up still doesn't show").
2. **Chrome, Edge, Brave and Opera** (a computer): paste `chrome://flags/#unsafely-treat-insecure-origin-as-secure` (`edge://flags/...`, `brave://flags/...`, `opera://flags/...`) in the address bar (a page cannot open it for you); in the box put the origin of the page with its port (`http://192.168.1.20:7303`) and set the choice to Enabled; click Relaunch; reload the page.
3. **On a phone** the sound and the tab alert work; pop-ups need HTTPS (and many phone browsers want a service worker for them), which a page served by the daemon on the network does not have.

After the reload the page is a secure context, the two choices with a pop-up are there and **Test pop-up** works; choose **sound and pop-up** and answer the browser's question.

**An alert when no page is open.** The page alerts only while it is open somewhere. To be told when no page is, make the alert command push to your phone: for example, with the [ntfy](https://ntfy.sh/) app subscribed to a topic, `messages/alert_command` can be `curl -s -H "Title: APRS message from $NEOAPRS_FROM" -d "$NEOAPRS_TEXT" https://ntfy.sh/<your-random-topic>`. An ntfy.sh topic is public to whoever guesses its name, so make it long and random (or run your own ntfy server); what a message says goes through that server.

**The message board: bulletins and group messages.** A message addressed to `BLN0`..`BLN9` (a bulletin), to `BLNA`..`BLNZ` (an announcement), to `BLN` and a number or letter and then a group name of up to five characters (`BLN3HAMS`: a group bulletin, group `HAMS`) or to `ALL`, `CQ` or `QST` (a group message), or to the weather service (`NWS-xxxxx`, `SKY`, `CWA`, with up to three more characters for the last two: kind `nws`) is no conversation: it is never acked, whatever id it carries, it is not a row of the table `message` (not even an `overheard` one) and it is not in the Messages tab. The inbox hands it to the message board (`services/bulletins.py`), which holds one entry for each **sender and slot** (the slot is the addressee as written, in capitals: `BLN1`, `BLNA`, `BLN3HAMS`, `QST`; a message gated by an iGate is from the sender inside it). A sender sending the slot again replaces the text: the entry starts again with one hearing and `first_heard` is when the new text was heard; the same text again moves `last_heard` and counts one more hearing (`times_heard`; the copies of one transmission that come by different digipeaters within 10 seconds are one hearing). A message with no text adds nothing. The board is kept in the table `bulletin` (migration 7: `sender`, `slot`, `group_name`, `text`, `first_heard`, `last_heard`, `times_heard`, one row for a sender and slot, strict, with named CHECKs), so a restart finds it.
Nothing leaves the board on its own: no ageing, no limit, no daily prune; an entry stays, with its `times_heard` and `last_heard`, until the operator deletes it with the delete button (a trash can) on its row in the Bulletins tab (two presses, the second after "sure?"), which sends `bulletin_delete{sender, slot}`: the daemon removes the row from the board and the database and every page gets a `del` (an entry that is not there is an `error`). The same bulletin heard again afterwards is a new entry, heard once. On the wire it is the topic `bulletins`, `{sender/slot: BulletinRow}` (`OH2XYZ/BLN1`), a `set` for a bulletin that is new or heard again and a `del` for one that is deleted; a row has `sender`, `slot`, `group`, `kind` (`announcement`, `bulletin` or `group`: a group bulletin and the messages to `ALL`, `CQ` and `QST`), `text`, `first_heard`, `last_heard` and `times_heard`. The Bulletins tab of the page shows the board newest first in three sections (announcements, bulletins, group messages); see "The page".

**Queries.** A message to us (our call with its SSID, exactly; the text is read without regard to case or blanks) whose text is one of these is answered by `services/queries.py`, with frames of our own (not messages of messaging: none is kept as a message, retried or waited for), by the path of the asker (the station preferences, else `beacon/path`; for a third-party packet the asker is the sender inside):

| query | the answer |
|---|---|
| `?APRSP` | our position packet, the beacon's own frame (`Beacon.frame()`): `OH2GBA>APZNEO,WIDE1-1,WIDE2-1:=6010.20N/02456.40E-NeoAPRS` |
| `?APRSS` | our status report as it was last sent, with the time of the answer (`>211200zQRV 14.074 MHz USB`); nothing while none has been sent (the one kept from before a restart counts) |
| `?APRSD` | a message to the asker with the calls heard direct in the last hour, the one heard last first: `OH2GBA>APZNEO,WIDE1-1,WIDE2-1::OH2RDG   :Directs= OH2RCH-2 OH2PU-9`. At most 67 bytes of text; when the calls do not fit it is two messages, each starting `Directs=`, and what does not fit in two is left out. `Directs= none` when no station was heard direct in the hour. Stations are those of the station book (not us, not objects); "heard direct" is a packet with no repeated digipeater that was not a third-party packet |
| `?APRST`, `?PING?` | a message to the asker with the header of the query as we heard it, the digipeaters it went by with their stars: for a query from OH2RDG to `APZNEO` by `WIDE1*,OH2RCH-2*,WIDE2-1`, `...::OH2RDG   :Path= OH2RDG>APZNEO,WIDE1*,OH2RCH-2*,WIDE2-1`; the last digipeaters go when it would be over 67 bytes |

The general query `?APRS?` is a `?` packet, the start of the information field, and not the text of a message (a message with that text is not answered, whoever it is for); it is answered with our position packet (the beacon's frame again) and then our status report (only when one has been sent in this run or is kept), after a random wait of 0 to 120 seconds, and once taken another is not taken for 10 minutes (the one that is waiting counts). It may carry the specification's target footprint, `?APRS?V34.02,-117.15,0200`: the latitude and longitude in degrees (the V stands for a space and may be left out, a west or south value has its minus) and the radius in miles; then we answer only when `station/lat` and `station/lon` are inside the circle, and a footprint that does not read is not answered. The answers are not retried and not sent while the TNC is not connected (the log says so). The answer has no id. The same query from the same station within 30 seconds (the copies of one transmission by different digipeaters, an impatient asker) is answered once; a query that cannot be answered (the settings make no frame) is told in the log. The suite never opens the radio: try the queries live with a station that can ask (`?APRSP` from another radio or from aprs.fi's message form).

**A path for each station.** A station can be given a path of its own, the digipeaters that everything we send to it goes by way of: the messages, their repeats and the acks of the messages it sends us. It is up to 8 digipeater calls separated by commas, checked as `beacon/path` is; an empty path is a path of its own, direct with no digipeaters, which is not the same as none set. A station without one has `beacon/path` (the page writes "(default)" then). The path belongs to the call as written, so OH2RDG and OH2RDG-7 have one each; a change counts from the next frame (a message that is being sent goes on by the new path), and the paths are operator data in the table `station_pref` of the database, not part of the station cache, so they survive a rebuilt cache and a restart. On the page the path is the field under "Route" of a conversation (the Message button of the station's card opens the conversation; the **Route** button in its header opens the path, and has a dot when the station has a path of its own or is RF only); it is saved when the field is changed and left (Enter does it), and the x beside the field takes it away (the station has the default again; the placeholder of an empty path is "direct"). On the wire: the topic `station_prefs` and the commands `set_station_path` (an empty `path` is direct) and `clear_station_path`.

**How a packet reached us.** The path of a received packet lists up to 8 digipeaters, and each has a has-been-repeated bit (the star in the text form, `OH2RCH-2*`). A digipeater that repeats a packet usually puts its own call in place of the alias it used (`WIDE1-1` becomes `OH2RCH-2*`), so the starred addresses, in order, are the route, and the last of them is the station whose transmission we heard. A starred alias (`WIDE1*`, `WIDE2-1*`, `TRACE2-1*`; `WIDE`, `TRACE`, `RELAY`, `ECHO`, `GATE`, `TEMP`, `TRACK` and `SAR` with a digit and an SSID) is a hop whose call we do not know: an anonymous one, written `?`. An address without a star has not been used and is not part of the route, and a packet with no starred address at all came straight from its sender. `OH2RCH-2*` is "via OH2RCH-2", `OH2RCH-3*,TRACE2-1` is also "via OH2RCH-3" (the alias after it was not used), `WIDE1*,OH2RCH-2*,WIDE2-2` is "via ? → OH2RCH-2" and `OH2RCH-1*,OH2RCH-3*` is "via OH2RCH-1 → OH2RCH-3" (`neoaprs/route.py`). The route is worked out when the packet is heard: it is `route` on every packet of the topic `packets` (empty for the ones we sent) and on every message that came in or was overheard (kept with the message, in the column `route` of the table `message`, so the thread shows it without the packet; of the two copies of a message that arrive by different routes the first one heard is the one that is kept, and both copies stay in the packet log with their own paths).
The station book counts, for each station, how many of its packets came direct and how many by each route, from the packets heard since the start and, at the start, from the latest 2000 packets the database kept; it keeps the 8 most frequent routes of a station (when a ninth comes the one with the fewest packets goes, the one heard longest ago first). The row of the topic `stations` has `last_route` (how the latest packet came), `heard_direct`, `heard_via` (`[station heard, packets]`, the most first, `?` for an anonymous last hop), `best_route` and `suggested_path`. The best route is the one most packets came by, direct included; with equal counts the one with fewer hops wins, then the one heard last. The suggestion is that route turned round, because the station that repeated the packet last, nearest to us, is the first digipeater of a packet we send back: direct suggests an empty path (direct), "via OH2RCH-2" suggests `OH2RCH-2`, "via OH2RCH-1 → OH2RCH-3" suggests `OH2RCH-3,OH2RCH-1`. When the best route has an anonymous hop there is no call to name for it, and the suggestion is the general form `WIDE1-1,WIDE2-1` (the card then says "unknown repeater"). No route is known (`suggested_path` is null) for an object or an item, for our own station and for a station none of whose packets are left.
**Heard direct.** The station book also keeps when each station last came direct, with the counts above: `Deliveries.last_direct_at`, the time of the latest packet with no repeated address in its path (not a third-party packet), from the packets since the start and, at the start, from the latest 2000 that the database kept (a station's time is that of its latest direct packet among them). The row of the topic `stations` has it as `last_direct_at` (null for a station never heard direct, and for us and for objects). The share of a station's packets that came direct is `heard_direct` over all the packets counted for the station (direct, by a digipeater, from the internet), not over `packets`, which counts from the first time it was heard whatever was pruned. The page shows it in the Stations table, on the map and on the card ("The page" below), and `?APRSD` answers with it.

**Third-party packets.** An iGate that hears a station on the internet (the ack of a message we sent, a reply) puts it on the air wrapped in a frame of its own with its own call as the source, `OH7JHF-1>APRS,OH2RCH-3*:}OH2DPN>APJYC1,TCPIP,OH7JHF-1*::OH2GBA   :ack10`: the information field starts with `}` and holds a whole packet in the text form, `SOURCE>DESTINATION,PATH:information`. The Tnc opens the wrapper (`neoaprs/aprsthirdparty.py`; one level only, a wrapper inside a wrapper, or one whose header is not a header, stays "third-party" and is not read): the packet keeps the gate as its `source` and the path it was heard by, `raw` and `info` are untouched, `decoded` is what the packet inside says (read as from its inner source to its inner destination, which Mic-E needs), and `third_party` holds the inner header (`via` on the wire is the gate; the summary ends "via OH7JHF-1 (third-party)"). From then on the sender of the packet is the one inside: an ack or a rej from it settles our message, a message from it is received and acked to it (by its path, or `beacon/path`), a position or an object report updates its station and not the iGate's (the iGate is no station of ours for that packet and never appears at that position), a packet with our own call inside is ignored as an echo is, and a message heard both direct and from a gate is one message (the repeat rule above). The route of such a packet starts at the gate: "via OH7JHF-1 (internet)", or "via OH7JHF-1 (internet) → OH2RCH-3" when the gate's frame was repeated. It counts for the station book as "from the internet" (`heard_gated`) and **never for the suggested path**: the gate is not a digipeater of the way back, the sender is on the internet and nothing says it can be reached by RF through that gate. Only packets heard direct or through digipeaters make a route to suggest. (The gate itself is a station when it sends packets of its own.)

**The unconfirmed state.** Some stations never ack to us: the email gateway's acks reach us only if an iGate within reach puts them on the air, and a station that is not listening at all will never answer however often it is told. A message whose `attempts_max` is 1 or 2 (the gateway's, a bulletin's, or an older one given so few) that has used its attempts without an ack is not a failure, since no ack was ever expected: it becomes `unconfirmed` (the wire's `state`, a hollow check on the page, "sent, no ack expected"; the thread says "sent once, no ack" or "sent twice, no ack") and the cross is kept for a message that was given 3 attempts or more. An ack or a reject that comes later still settles it, like any message that is not settled, and Retry sends it again as it sends a failed one.

**A timeout for each station.** A station whose last position is older than 3 hours (180 minutes, fixed: `HIDE_AFTER_MIN` of `neoaprs/config.py`, no setting; a `map/hide_after_min` stored by an earlier version is ignored) leaves the map (the page hides it; it stays in the Stations table, and in the database until the daily prune removes it). A station can have a timeout of its own beside its path, in the same row of `station_pref` and under the same call (or, for an object or an item, its name): the minutes after its last position, 0 is never, none set means the 3 hours. The daemon only keeps and tells the number (`set_station_timeout` and `clear_station_timeout`; the topic `station_prefs` carries `{path, hide_after_min, rf_only}` for each station, the first two null where none is set, and an entry with neither and `rf_only` false is not kept; the column `attempts` of `station_pref` is no longer read or written, and a row that holds only that says nothing), except for one thing it does itself: the daily prune keeps a station with a timeout of 0 in the station book and its cache row whatever its age (its packets and messages are pruned as the others are).

**RF only.** The APRS-IS rules say an iGate does not put on the internet a packet whose path holds `NOGATE` or `RFONLY` (an iGate may honour that, it is not required to; `TCPIP` and `TCPXX` it must). A station can be marked RF only, the fourth part of its row in `station_pref` (the column `rf_only`, 0 or 1): from then on every frame we send to it, each attempt of a message, each ack of one of its messages and each answer to one of its queries (`?APRSP`, `?APRST`, `?PING?` and the others), has `RFONLY` as the last element of its path, after the station's own path or else `beacon/path` (`PrefBook.path_for` adds it, so every one of those frames takes the same road). A path that holds `RFONLY` or `NOGATE` already gets no second one. A path of 8 digipeaters has no room for it: a message to the station is refused with `path too long for RF only`, an attempt that is due waits (it is not used up; the log says why once, and it goes when the path is shorter or RF only is off), and an ack or an answer is not sent (a line in the log). The email gateway `EMAIL-2` is on the internet and can never be RF only: `set_station_rf_only{call, on: true}` for it is an `error` with that reason, and the Email tab has no tickbox. On the wire: `set_station_rf_only{call, on}`, answered by the `set` of the entry in `station_prefs` (or its `del` when `on` is false and nothing else is set). The delivery chain does not show what is no hop: `RFONLY`, `NOGATE`, `TCPIP`, `TCPXX`, `NOTCP` and the q-constructs (`qAR` and the others) are left out of the hops of an attempt, in what is kept and what the page is told, and of the heard path when hops are read from it; an attempt stored with one of them shows without it. On the page the tickbox "RF only" stands beside the path, in the header of a conversation (its title: "iGates do not put these messages on the internet"); it is saved when it is ticked or cleared.

**What is kept.** Every message is stored while the daemon runs: each message to us, each message we send with every change of its state and attempts (the table is written as it changes), and the ack or reject we receive on the message it settles (`acked_at`, `state`). A message to another station that we only hear is kept too, as `overheard` (a message to a bulletin, an announcement, a group, `ALL`, `CQ`, `QST` or the weather service is the board's, not this; a query and a telemetry definition are in the packet log only) (direction `in`; the sender in `from_call`, who it is for in `to_call`), once for a repeat or a digipeater's copy within 30 minutes (by its id and text, or by its text when it has no id) and never acked; the acks and rejects of other stations are not messages and are not kept. Overheard messages are no conversation: the page lists them only when "Show overheard" is on (off by default, remembered), a pair of stations at a time. Nothing is dropped: the daemon holds every message, overheard ones included, and the page is given all of them (no window, no count limit, and the daily prune leaves the messages alone, whatever the 7 days of the prune say); a message goes only when the operator deletes it (the x of a conversation, `conversation_delete`, or `message_delete`). The one bound is a database with more than 10000 messages: a start then takes the latest 10000 and says so in the log as a warning, and the older ones stay in the database.

**Deleting.** `message_delete` removes a message of any kind (ours, one sent to us, one only overheard) from the database, from the daemon's records and, by a `del` of the topic `messages`, from every page; one that is still being sent is cancelled first, so that no attempt is made while it goes, and an id the daemon does not hold is an `error`. A message that is deleted and heard again within 30 minutes is not kept again (the repeat rule above). The command stays in the wire and in the daemon, but the page has no button for it: a single message is not deleted from the page, and the x on a conversation's row (below) is the one way to delete there (the board's x deletes a bulletin).

**Deleting a conversation.** `conversation_delete{call}` removes the whole conversation with a station: every message we sent to it (direction `out`, `to_call` the call) and every one it sent to us (direction `in`, `from_call` the call), from the database in one write (`messagesql.delete_conversation`), from the daemon's records and, by a `del` for each message, from every page. The messages that are being sent are cancelled first, so that no attempt is made while it goes; the messages we only overheard (the station sending to others, others sending to it) are not part of a conversation and stay; the station's path and timeout stay too, they are the station's and not the conversation's. The call is read as a call (`oh2rdg` is `OH2RDG`) and the SSIDs are different stations (`OH2RDG-7` is not `OH2RDG`). A call with no message is an `error`, and so is a database that would not take the removal (the messages are then kept, those that were being sent cancelled).

**Deleting what was overheard.** `overheard_delete{from_call, to_call}` removes every message we only overheard `from_call` sending to `to_call` (state `overheard`, that sender and that addressee, the pair as the list shows it) from the database in one write (`messagesql.delete_overheard`), from the daemon's records and, by a `del` for each, from every page. The conversations are not touched: a message we sent or one sent to us is never removed by it. A pair with no overheard message is an `error`, and so is a database that would not take the removal.

**On the page.** The Messages tab is laid out like Signal, by the width of the tab itself (the panel beside the map, not the window: the panel can be narrow on a wide screen). From 600 px on (a list of 240 px, a divider and a conversation of at least 359 px, which holds the box to write in and bubbles that can be read) there are two columns: the list of conversations at the left, the open conversation at the right, a vertical line between them; with no conversation open the right side is quiet and says "Choose a conversation, or a station's Message button". Under 600 px (a phone, a narrow panel, the default width of 480 px) one of them fills the tab at a time: the list until a conversation is picked, then the conversation with a back arrow "‹" at the left of its header (Esc does the same, on a wide tab too) that returns to the list, with the focus on the row it came from. Resize the panel (the handle at its left edge) or the window and the layout follows, with the same conversation open.

**The list.** The conversations, the one with the newest message first; a row has the call (an overheard pair as "OH2AAA > OH2BBB"), the age, the last text on one line ("You: " before one of ours) and the number of messages that came in since the user last looked at the conversation, and a trash can at its right end. The open conversation is the filled row; a conversation with messages not seen that is not the open one has its text in bold and a bar at its left. A row is a button, so the list is walked with Tab. There is no "New message" button: a chat starts from a station, with the Message button of its card on the map (or in the stations table), which opens the conversation with it, or creates it when there is none yet. "Show overheard" (with an (i)) is at the top of the list. What was seen is the highest message id of each call, kept in the browser (`localStorage`). A message counts as seen only while its conversation is open **and** visible: the Messages tab is the tab on show **and** the panel is not folded **and** the page is visible (`document.visibilityState`, so a page in a background browser tab keeps counting) **and**, on a narrow tab, the conversation is the one shown and not the list (going back to the list is leaving the conversation: messages that come in then count again). The count of messages not seen is shown as a badge on the Messages tab, on the handle of the folded panel, in the header (a click opens the newest conversation with something new) and in the title of the browser tab (`(2) NeoAPRS`, plain `NeoAPRS` with none).

**The conversation.** Its header has the call (the back arrow at its left on a narrow tab) and a small **Route** button at its right: the path the messages to the station go by (with the suggested one) and the tickbox RF only open in a box under the header, closed again by Esc or a click outside; a dot on the button says that the route is not the default (a path of its own, or RF only). An overheard pair has no Route. The thread is bubbles, ours at the right and theirs at the left, filling the height and scrolled to the newest: the text, and under it, small, the time, for ours the mark and the state with the attempts ("attempt 3 of 4" while it is being sent) with Retry or Cancel where they apply, and under ours the chain of the digipeaters its packet went by; for a message that came in, the route it came by in small type ("via OH2RCH-2"). At the bottom, always in view, is the box to write in, in one line: the text, the bytes left of the 67 ("67 left") and Send, which is off while the TNC is not connected or the text is empty or too long. It has no To and no list of stations: the conversation is the station (the Message button of a station's card, which on a narrow tab goes straight to the conversation, opens it). An overheard pair has no box to write in at all, and no Route: only the bubbles and the delete in the list, since the messages are not ours to answer. What was typed stays when the user goes back to the list or opens another conversation. Esc deselects the open conversation, on a wide tab as on a narrow one (the right side is quiet again, on a narrow tab the list is back, with the focus on its row): the Route box, if it is open, takes the first Esc; a text box with text in it keeps the text and the conversation, and with it empty Esc goes through; the list of conversations has nothing to deselect. Each message of ours has a small mark: a clock while it is being sent (its title says "attempt 3 of 6"), a check once it is acked (its title has the time of the ack), a hollow check, a ring with a check in it, when it was sent and no ack is expected (`unconfirmed`, the title "sent, no ack expected"), a cross when it failed or was rejected (the state as the title) and a dash when it was cancelled; a message that came in has its time only. A click on a row opens that conversation (a click on the open one keeps it open); the Message button of a station's card always opens the conversation. The trash can at the right end of each row deletes the whole conversation with `conversation_delete`, or (on an overheard pair, listed with "Show overheard") every overheard message of the pair with `overheard_delete`, after two clicks ("sure?" for 5 seconds, like the other buttons that ask twice); the conversation closes if it was the open one (the right side says "Choose a conversation", on a narrow tab the list is back). A single message has no delete button.

**One text to several stations.** The page opens the **group compose** for a list of calls (`openGroup(calls)` of `useMessagesView`, which the map's station cards call from "Message these 3" after Ctrl+click on several stations; a call that is no call, `EMAIL-2` or a repeat is left out, the Messages tab is brought to the front and the open conversation is left). It takes the place of a conversation, with the list beside it on a wide tab and instead of it on a narrow one: its header has the recipients as chips, each taken out by a click on it (the last one out closes it), a close button (on a narrow tab the back arrow "‹"), and at the bottom the text, "67 left" and **Send to 3**. Esc closes it (not while its text box has text in it, as in a conversation). Send does what the Stations list used to do: the page sends one ordinary `send_message` for each recipient, each message with its own id, acknowledgement, attempts and conversation, exactly as if sent one by one, and nothing different goes on the air. They leave one after the other at the pace above, and each conversation shows its message as usual (`sending`, then `acked` or the rest). The group compose then closes and nothing is opened; the conversations are in the list. A conversation opened meanwhile (a Message button, the mail in the header) closes it. What is typed in it is kept apart from the drafts of the conversations.

**Email.** The APRS email gateway is the APRS-IS station `EMAIL-2` (aprs-is.net/Email.aspx). It is on the internet, not on the radio: a mail reaches it through an iGate that hears our radio and puts the packet on the internet, and its acks and answers come back through an iGate within reach of our radio that puts them on the air. With no iGate in reach nothing gets through, and a mail that did get through can still look unanswered. Mail is an ordinary numbered message to `EMAIL-2` whose text is the addressee, a space and the text, one line of at most 67 characters in all (for us the same 67 bytes of UTF-8 as any message: `jane@example.com Hello Pekka`, so the address and the space take their share of the 67). The addressee is an address or the name of a shortcut. A shortcut is a name for an address, made by sending the address once with the name in front, `me jane@example.com`, and used from then on as the addressee, `me Hello`; a name is letters and digits, and belongs to the call that made it. It does a second thing: only the people who are shortcuts of a call can email that call, and their mail arrives as an APRS message from `EMAIL-2` (they put `CALLSIGN-SSID:` first in the subject of the mail). `name L` makes the gateway email the list of the call's shortcuts to that shortcut's address, and `name R` removes it. The page does not use shortcuts: it sends to addresses (a name that is already a shortcut of the call at the gateway still works when it is typed in To), and it shows a shortcut command in the history as the plain mail it is on the wire. `get` fetches the mail the gateway holds for us: mail from a shortcut that our radio did not acknowledge (4 tries, a minute apart) is held for 24 hours, and `get` makes the gateway send all of it, 10 seconds apart. The gateway's acks and status replies come back as ordinary messages from `EMAIL-2`; they reach us through an iGate that hears the gateway on the internet and puts them on the air as third-party frames, which the daemon unwraps ("Third-party packets" above), so an ack arrives only where an iGate within reach of our radio does that. The gateway serves interactive stations only and blocks a station that sends in the blind; ours is interactive: a person types each message. The daemon has nothing special for any of this: the wire is `send_message` to `EMAIL-2` and the messages of the topic, as for any station. On the page the Email tab (after Messages) is a mail list and not a conversation: one row for each message to or from the gateway, the oldest first and scrolled to the newest at the bottom, as the Messages tab is, with no bubbles. The list fills the tab, between the top and the box to write in, and has the same structure as the Bulletins board. At the top is the one button **Check email** and a small (i) with two short sentences: mail goes through the gateway and an iGate, so it may show "Not confirmed" although it arrived, and Check email asks the gateway for the mail it kept for us (24 hours). **Check email** sends `get`: the gateway sends again the mail it kept for us (the row in the list reads "Checked email", with its state). It is off while the TNC is not connected and, "Already checking", while a `get` of ours is still being sent, so the gateway is not asked twice. At the bottom, always there (the same box as the other tabs have to write in, no button opens it), is the box for a mail: "To" (an email address; while the box has the focus the addresses used before that match what is typed are listed under it, opening upward over the list, kept in the browser with the newest first: a click picks one, and the trash can beside it forgets it), "Text", "N left" for the characters left of the 67 over the address, the space and the text, and **Send** at the lower right. Send (the line `address text`) is off while the TNC is not connected, the address or the text is empty, the address has a space in it, or the line is more than 67 bytes. After Send the text is empty again and the address stays, for the next mail to the same person; the mail is the last row of the list, "Sending". **The list.** A mail of ours is "To jane@example.com" over its text (one line; a click on the row opens it to show the text whole, with the date and time, the route and the chain of digipeaters of its latest attempt), the time, and its state in words with its mark: "Sending (1 of 2)" with the clock (the attempt of the 2 the gateway is given; "Waiting for the radio" before the first), "Delivered" with the check (the gateway acked it), "Not confirmed" with the hollow check (sent twice, no ack: not a failure, since the gateway may well have the mail, also for an older message that was given 3 attempts or more and that the daemon calls `failed`; a late ack still settles it), "Rejected" with the cross, "Cancelled" with the dash. Retry (for a mail that is not confirmed, rejected or cancelled; it may mean twice to the gateway) and Cancel (while it is being sent) are small buttons on the row, and the trash can in its corner deletes the row after a second press ("sure?", `message_delete`: the row goes from the daemon and from every page). The `get` of Check email is a row in words with the same states, "Checked email". What the gateway sent is "From EMAIL-2" over its text (its replies); when its text starts with an email address and a blank (`jane@example.com Hello`, also `<jane@example.com> Hello` or `jane@example.com: Hello`) the row is taken for mail the gateway forwards to us and reads "From jane@example.com" over the rest of the text, and the page shows any other text as the gateway's. The gateway's acks are no rows: they settle the state of the mail they belong to. A row that came in while the Email tab was not on show is bold with a bar at its left, and stays so until the tab has been left and is opened again. The tab's badge counts the messages from `EMAIL-2` not seen, under the same rules as the Messages tab's (the Email tab on show, the panel open, the page visible), and the browser tab's title counts both. `EMAIL-2` is not among the conversations of the Messages tab and its messages are not in that tab's count; its compose box refuses `EMAIL-2` as the addressee ("Use the Email tab"), and the Message button of the gateway's station card opens the Email tab.

A first message on the air is not tested by the suite (it never opens the radio): check it live with a station that answers, and look at the packet log for the message, the ack and the repeats.

### Objects and items of our own

The Objects tab of the page makes an object or an item, shows it on the map as ours, changes it and kills it, and the daemon sends it on the air by a schedule of its own (the commands `object_set` and `object_kill` and the topic `own_objects` of `PROTOCOL.md`). An object (`;`, chapter 11 of the specification) has a name of 1 to 9 characters and a time stamp; an item (`)`) has a name of 3 to 9 characters and none. Objects of other stations that we hear are stations of their own on the map, named by the object and marked with who reported them; a copy of one of ours that comes back is none of them (below).

**Making one.** New opens the form at the bottom of the tab, under the list of our objects (oldest first, scrolled to the newest, so that it is next to the form), in the box that every tab writes in (its fields scroll on a short screen; the line under them has **Pick on the map** at the left and, at the right, "N left" for the comment, Cancel and Save), at the place we are: the name (printable ASCII, case-sensitive, none of `!`, `_`, `|` and `~`, no blank at either end; never our own call, and never the call of a station that was heard), object or item, the symbol (a picture and its name, as in the Beacon tab: Change opens the picker), the position (typed, or **Pick on the map**, a button at the left of the line with Cancel and Save, and a click on the map: the form shows a pin where it is), a comment (43 characters, 36 behind a course and speed), the course in degrees and the speed in km/h (each or both or neither) and the path (the placeholder is `beacon/path`, which an empty field means; up to 8 digipeaters, and `RFONLY` or `NOGATE` in it keeps the iGates from putting it on the internet). A field with something wrong is red, and its title says what; Save waits until nothing is wrong. Save sends `object_set`: a name that is there is changed. There are at most 50 objects and items of ours at once, and nothing is made while the call is not set (the interlock, below). **The map:** an object of ours has a dashed ring and a marker that can be dragged: where it is dropped is its new place (the same as a change in the form, with everything else as it was). It never times out. Its card has Edit (the Objects tab opens with it) and Kill, in place of Message and Forget, and none of a station's fields. In the Objects tab each object has Edit and an x, which asks twice (the second press after "sure?") and kills it; a row says how often the object was sent and when it goes out next ("sent 3 times, next in 12 min"), "waiting" when that time has passed because the radio is away, and "killing" for an object whose kill is going out.

**The packet.** An AX.25 UI frame from `station/call` to the tocall by the object's path, else `beacon/path`. The information field is the object's `;`, its name padded with blanks to nine characters, `*` for a live object, the time stamp, the position, the course and speed when it has them and the comment; the time stamp is the day, hour and minute of the moment of sending in UTC with a `z` (the specification recommends zulu time only), so each copy carries its own. The position is the uncompressed form rounded to the hundredth of a minute; the course is `CSE/SPD`, three digits of degrees (360 is north, 000 is none) and three of knots. These are the specification's own examples:
`OH2GBA>APZNEO,WIDE1-1,WIDE2-1:;LEADER   *092345z4903.50N/07201.75W>088/036` (an object at 2345 hours zulu on the 9th, heading 88 degrees at 36 knots) and
`OH2GBA>APZNEO,WIDE1-1,WIDE2-1:)BRENDA!4903.50N\07201.75W@088/036` (an item: `)`, the name, `!`, no time stamp; the Hurricane Brenda symbol `\@`).
A killed object or item is the same packet with `_` where the `*` or the `!` was: `;LEADER   _092345z4903.50N/07201.75W>088/036`. The table of data types of the specification lists a `-` in front of the name for a killed object, which no program on the air reads; every APRS program kills with the `_`, and so do we (our own parser reads it back).

**When.** The decay algorithm of the specification's "Packet Timing" (chapter 2: transmit a new packet once and n seconds later, double n each time, and when n reaches the net cycle time continue at that rate): a new or changed object goes out at once, then after 1, 2, 4, 8 ... minutes, never more than the net cycle time of its path apart, until it is changed (the decay starts again) or killed. The net cycle time is the specification's, by the digipeaters of the path (chapter 2, point 4): 10 minutes direct or by one digipeater, 20 by two (`WIDE1-1,WIDE2-1` is two: the default), 30 by three or more; a `WIDEn-N` counts the N hops it has left and `RFONLY`, `NOGATE` and the markers of the internet count none. So with the default path the packets are 0, 1, 3, 7, 15, 31 and then every 20 minutes (51, 71 ...); with `WIDE2-1` they are 0, 1, 3, 7, 15, 25 and then every 10; with `WIDE3-3` 0, 1, 3, 7, 15, 31, 61 and then every 30. No packet of one object goes out less than a minute after the one before it, a change included (a change asked for sooner waits), and at most one packet of ours of this kind (an object or a bulletin) goes out every 10 seconds, whatever is due, so that a restart with many objects, or a radio that comes back, sends no burst. A **kill** is sent three times (at once, a minute later and three minutes after the kill), and then the object is forgotten: removed from the database and from the list; it leaves the map as soon as it is killed. An object that was never sent is removed at once and nothing is said of it.

**The interlock and the radio.** Everything of this goes through the transmit interlock (`config.can_transmit`) and the Tnc's own check: nothing is made or sent while `station/call` is not a call (the log says `no object sent: set your call first`, once), and nothing is sent while the radio is not usable (the Tnc is not connected, silent, not yet confirmed or settling after KISS ON). What is due then is not skipped and not made up: the log says once per outage `the object is due and the radio is silent: it goes out when the radio is back`, and the first moment the radio is usable one packet goes out for each object that was due, however many intervals went by, and the schedule goes on from there. A frame that cannot be made (a `beacon/path` of more than 8 digipeaters) is told once, and the objects that have a path of their own are not held up by it. **Nothing is tried on a real radio by the tests:** the first transmission is to be checked live (an object made, then looked for on aprs.fi or on another station's screen) before objects are left on the air.

**Heard back, and taken over.** A packet from our own call that comes back (a digipeater's copy of our object, an iGate's, the TNC's echo) is no report of an object: the station book counts it as proof that we are heard (it moves the time we were last heard) and does nothing else, so there is never a second object of the same name, and the packet is in the packet log as any packet heard. The specification's "Replacement" (any station may take over reporting an object by sending it, and the original station ceases to transmit it) is kept: when another station reports a live object with the name of one of ours, ours is dropped without a kill (the log says who took it over) and the map shows theirs; another station's kill of the name does not end ours.

**Kept.** The table `own_object` of the database (migration 13: name, kind, position, symbol, comment, course, speed, path, whether it is alive or being killed, when it was made and last changed, how often it was sent since then, when last; strict, with named CHECKs), written after every change and every packet, so a restart goes on where the schedule stopped: the objects are on the map at once, nothing is sent for the restart, a kill that was not sent yet is sent, and the next packet is due when the schedule says. Our objects are not in the station cache of the database (the table `station`). On the wire the topic `own_objects` has the values and the schedule of each (`state` `live` or `killing`, `sent`, `last_sent_at`, `next_at`), the topic `stations` a row with `own` true for each live one.

### Posting to the message board

The Bulletins tab has a box at its bottom to post to the board, under the board, which fills the tab and stays newest first in each of its sections (it is read from the top; a stream oldest first would open on the weather service) (the commands `bulletin_post` and `bulletin_unpost` and the topic `own_bulletins` of `PROTOCOL.md`): the kind (a bulletin, an announcement or a bulletin to a group), the identifier, the group name of a bulletin to a group and the text, and under them, at the right, the characters of the 67 it has left and Post. A small (i) beside the kind says what they are: a bulletin is for everyone and nobody acknowledges it; a bulletin to a group is for the stations that follow that group name; to reach particular stations, with an acknowledgement from each, send them a message (Messages tab, Stations). A **bulletin** is `BLN0` to `BLN9`, an **announcement** `BLNA` to `BLNZ`, a **bulletin to a group** (a group bulletin) `BLN`, a number and a group name of one to five letters and digits (`BLN3HAMS`); the text is at most 67 characters of printable ASCII without `|`, `~` and `{`. Post is on when it can be sent. The messages to `ALL`, `CQ` and `QST` and the weather service's are not posted from here.

**The packet.** A message without an id (chapter 14 of the specification), by `beacon/path`: `:BLN3     :Snow expected in Tampa RSN` (the specification's bulletin: the addressee padded to nine characters), `:BLNQ     :Mt St Helen digi will be QRT this weekend` (its announcement) and `:BLN4WX   :Stand by your snowplows` (its group bulletin). Nobody acknowledges one, so it is sent more than once: **a bulletin** (and a group bulletin) at once, after 2 minutes, after 6, and then every 20 minutes until 4 hours after the first ("a few times an hour for a few hours"): 14 packets; **an announcement** at once, after 2 minutes, after 6, and then every hour until 72 hours after the first ("less frequently but perhaps for several days"): 74 packets. A text posted to a slot that holds one replaces it and starts the schedule again (never within a minute of the last packet of the slot); the same text posted again, once the schedule is over, goes out again. There are at most 36 of ours at once. The interlock, the radio that is away, the pause between two frames of ours and the restart are as for the objects, above: nothing is posted while the call is not set, what is due waits for the radio, and one packet goes out when it is back.

**On the board.** Ours are in the board in their section, under our call, marked "ours", with how often each was sent and when it goes out next, "ended" once its schedule is over (it stays until it is deleted or posted again). The delete button of an entry of ours asks twice and stops it and takes it off the board and out of the database (`bulletin_unpost`; its hover title says "Delete (stop sending)"); the one of an entry that was heard is the board's delete. **Heard back:** a bulletin of ours that a digipeater repeats comes back as a packet from our own call, which the inbox takes for a copy of what we sent (as it does for a message): it is not heard as a bulletin of another station, so the board of what was heard never holds ours, and `times_heard` of nobody changes. The table `own_bulletin` of the database (migration 13: slot, group, text, when posted, how often sent, when first and last) keeps them across a restart.

### Weather

A position whose symbol code is `_` (the weather symbol) and a positionless weather report (data type `_`) carry the weather fields after the position or the time: `c` or the leading `DIR/SPD` the wind direction (degrees; some stations send two digits) and speed (mph), `g` the gust (mph), `t` the temperature (degrees F, `t-05` below zero), `r` rain in the last hour, `p` in the last 24 hours, `P` since midnight (hundredths of an inch), `h` humidity (`00` is 100 %), `b` pressure (tenths of a hPa), `L` and `l` luminosity (W/m2, `l` is 1000 and over), `s` snow in the last 24 hours (inches, the `s` that follows the wind speed) and `#` the raw rain counter (`neoaprs/aprsweather.py`). A field that is all dots or all spaces is missing; the fields end at the first character that is not a field with its digits, and what follows (a software id such as `wRSW`, "RX Igate & WX station", a comment glued to the data like `b10285Inkoo`) is the comment. `Weather` holds metric values (wind and gusts in km/h to 0.1, temperature in degrees C to 0.1, rain in mm to 0.1, pressure in hPa, humidity in per cent, the direction in degrees, a direction over 360 is none), each `None` where the report did not have the field, and the fields as sent (`raw`); a report whose fields are all missing is no weather. It is `Position.weather` (the weather's fields are not the comment) and `Other.weather` for a positionless report (the packet's kind stays `other`, the table of packets is as it was); an object or item with the weather symbol has it on its position. The summary reads `position 60.4072 23.8788 /_ weather: wind 107° 2 km/h gusts 2, 10.0 °C, 85 %, 1028.4 hPa, rain 0.3 mm/h, 24 h 4.1 mm, today 3.3 mm - RX Igate & WX station`, only the fields that are there. A compressed weather position's `cs` bytes are the wind (direction `c`*4 degrees, speed 1.08^`s`-1 mph, the same coding as course and speed), and its fields after the 13 bytes are the rest of the weather.

**What else the parser reads.** Besides positions, objects, items, messages, statuses and weather (`neoaprs/aprs*.py`): the **data extensions** after the symbol of an uncompressed position are taken off the comment into `Position.extensions` (`PHGphgd` as power in W, height in m, gain in dB, directivity and the range the specification's formula gives, `RNGrrrr` in km, `DFSshgd`, the `/BRG/NRQ` of a DF report after the course and speed, and the `Tyy/Cxx` of an area object with the symbol `\l`); a compressed position has none, and the station card shows each on a line of its own. A `!` position may come after up to 39 characters of text (a digipeater of the X1J kind): the text is the start of the comment. A timestamp with `/` is the sender's local time: it is kept as sent with `Position.timestamp_local` set and shown as "09 23:45 local" in the detail of a packet, never converted; the MMDDhhmm of a positionless weather report is its time (`Other.timestamp`). **Raw NMEA** (`$GPGGA`, `$GPGLL`, `$GPRMC`, `$GPWPL`, any talker such as `$GN`; the checksum is checked when there is one) is a position with course, speed, altitude and time; its symbol is the one of the destination (`GPSxyz`, `GPSCnn`, `GPSEnn`, `SPCxyz`), else the icon of the source's SSID, else the unknown position; `$GPVTG` and a fix that is not valid stay "nmea", and `$ULTW` (an Ultimeter 2000) is "weather" without fields, because its format is not in the specification. **Telemetry** `T#sss,aaa,aaa,aaa,aaa,aaa,bbbbbbbb` is its own decoded type (`Telemetry`, packet kind `other`); the daemon keeps each station's latest report and the `PARM.`, `UNIT.`, `EQNS.` and `BITS.` messages addressed to it (in memory, the latest 500 stations, read again from the latest 2000 packets at a start) and sends the station row `telemetry` with the names, units and values `a*v^2 + b*v + c` applied (raw values when it sent no definition). `,` is test data ("test"), `<` station capabilities (`items`: `IGATE`, `MSG_CNT=2`...), `%` an Agrelo DF report (`bearing`, `quality`), `+` shelter data and `.` space weather (kept as text), `[` a Maidenhead locator beacon (a position at the centre of the square; the specification lists `[` as unused, so this form is the usual one and not the specification's). A **Maidenhead locator** at the start of a status report (`>IO91sx/-` and text after a space) is `Status.locator`, and in the status text of a Mic-E packet `Position.locator`; the station row has it as `locator` (the grid and the centre of the square), and it does not move the station. In a Mic-E packet the telemetry flag "`" is followed by two values of two hex digits, "'" by five, and 0x1d by five bytes (all dropped from the comment), and the altitude `xxx}` is read at the start of the status text (after the locator) or as a word of its own after a space.

**What is kept.** Every weather packet heard is a row of the table `weather` (`station`, `at`, `wind_dir`, `wind_kmh`, `gust_kmh`, `temp_c`, `humidity`, `pressure_hpa`, `rain_1h_mm`, `rain_24h_mm`, `rain_today_mm`, `luminosity`, `raw`; migration 8, STRICT with named checks, an index on station and time), appended without waiting (`neoaprs/weatherlog.py`); `at` is when the packet was heard, not the time it carries. A report that reaches us by two digipeaters is two rows. Rows are pruned after 7 days. **At the start:** when the weather table is empty, the controller reads the weather packets of the last 7 days from the packet table (a position, object or item whose summary shows the weather symbol, or a packet of kind weather; a third-party packet is the sender inside it), decodes each with the parser and writes the observations in one transaction, and logs how many; a table that holds anything is not made again. Then every station in the book is given its newest observation (`Station.weather` and `weather_at`).

**On the wire.** The row of `stations` has `weather` (the metric fields, null for a station that sent none) and `weather_at`; the command `weather_series{call, hours}` (1 to 168) is answered to the page that asked with `{"type": "weather_series", "call", "hours", "points": [[time, temp_c, pressure_hpa, wind_kmh, gust_kmh, rain_1h_mm, humidity], ...]}`, the oldest first, null for a value the report did not have. The card of a weather station (the weather symbol, or a station that has sent weather) opens with its weather panel: the readings (the temperature large, the wind as an arrow turned to where it goes with its speed, the direction it comes from and the gusts, humidity, pressure, rain over the hour, 24 hours and since midnight, luminosity and snow when sent) and how long ago they were heard, and under them the graphs of the temperature, the pressure, the wind with its gusts as a lighter band and the rain as bars, over the last 24 hours or 7 days (a switch, remembered), as inline SVG in the page's own colours (no chart library: `lib/chart.ts` is the arithmetic, `TrendChart.vue` one graph), with a line under the pointer that says the value and the time of the nearest observation. The page asks when the card opens, when the switch changes and when a new observation comes. The Stations table has a `wx` column with the temperature of a weather station (sortable; the title says how long ago), and the marker of a weather station keeps its symbol and has the temperature in its tooltip.

**The tracks.** The track of a moving station is kept in memory, so at the start it is made again from the packet table: the latest 5000 position packets heard within 7 days (a position, or a live object or item under its own name; the sender inside a third-party packet), oldest first, with the rule the live track has (a point joins when the station moved more than 10 m or 5 minutes passed; the latest 50 are kept). Our own station has no track.

### Without the radio

```bash
neoaprs replay                                                  # the sample capture of the package; prints socket://127.0.0.1:PORT, then sends one frame every 2 s once a daemon has connected
neoaprs run --data data --port socket://127.0.0.1:PORT          # in another terminal
neoaprs db --data data stations                                 # and in a third
neoaprs db --data data packets
```

The replay is a TCP server, so it works the same on every system; the daemon takes its address as the `--port` of this run (the setting `serial/port` is not changed). Nothing is sent while nobody is connected, and the frames go on from where they were when the daemon connects again. In a clone, `scripts/replay` and `scripts/neoaprs-db` are the same commands with the clone's `.venv` and `./data`.

SIGTERM, SIGINT and SIGHUP (on Windows Ctrl+C, SIGBREAK and SIGTERM) end the daemon the same way: the database thread does what was asked of it, the connection is closed, the exit code is 0. Exit code 2 means the database cannot be used (a newer NeoAPRS made it, or it is not a database) or another NeoAPRS is running on the same data folder: the service does not restart on it.

### As a service

`neoaprs service install` sets NeoAPRS up to start when you log in and keeps it running, the way each system does it, running this Python (`-m neoaprs --data DIR`) on the data folder given with `--data` (else the default). `neoaprs service remove` takes it away again (the data stays), `neoaprs service status` says whether it is set up and whether the daemon answers on its page (exit code 0 when both), and `neoaprs service logs` prints the end of `neoaprs.log` of the data folder.

* **Linux** writes a systemd user unit, `~/.config/systemd/user/neoaprs.service` (`$XDG_CONFIG_HOME/systemd/user`), from the template `neoaprs/cli/neoaprs.service` (`systemd/README.md`) with the interpreter and the data folder in it (the AppImage file when run from an AppImage), runs `systemctl --user daemon-reload`, `enable --now`, and `try-restart` when what the unit does changed; running it again after an update brings the unit up to date. The first line of the file says that `neoaprs service install` wrote it: a file there that it did not write is never touched (the command stops and says so). `--linger` also runs `loginctl enable-linger`, so that it starts at boot and survives a logout (without it the command says so, and the command to run); it checks that you are in the group that owns the serial devices and says the exact `usermod` command when you are not. `journalctl --user -u neoaprs -f` is the journal; `neoaprs service logs` the log file. In a clone, `scripts/install.sh` is `neoaprs service install --data ./data --linger` with the clone's venv, and the unit runs in the clone; `tests/test_service.py` and `tests/test_install.py` run it against a fake HOME and a fake `systemctl`.
* **Windows**: start at login for the current user: the value `NeoAPRS` of the key `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run` (the list that Settings > Apps > Startup shows), running `neoaprsw.exe run --data DIR`, or `pythonw.exe -m neoaprs run --data DIR` when NeoAPRS is not installed as a script; `install` also starts the daemon at once when none is running on the data folder. Not a Windows service: a service has no desktop and not the user's profile, and the COM port, the data folder and the page belong to the user who is logged in. `remove` deletes the value (a daemon that is running goes on until `neoaprs stop` ends it or you log out).
* **macOS**: a launchd agent, `~/Library/LaunchAgents/eu.oh2gba.neoaprs.plist`, loaded with `launchctl bootstrap gui/UID` and unloaded with `bootout`; started at login, started again 30 seconds after it ends with a failure; its own output (a traceback before the daemon logs anything) is `launchd.log` in the data folder.

The web page is on port 7303, on the loopback only unless the setting `web/network` is on ("Network access"); `--web-port N` takes another port for one run.

### Network access

The page answers on this computer only. To open it from another device on the same network (the radio and NeoAPRS on a Raspberry Pi in the shack, the page on a laptop or a phone at home): Settings tab, Web page, **Allow access from the network** ticked. It counts at once, with no restart: the page now also listens on every interface, on the same port, and the group shows the **access key** (three groups of four letters and digits, such as `k7m2-x9pq-4hrt`, made when the switch is first turned on) and **Open at**, the addresses of this computer on the network (`http://192.168.1.20:7303/`, and `http://NAME.local:7303/` with the name of the computer). On the other device open one of them and type the key into the one field of the key screen; the browser keeps the login for a year, so each device asks once. The log says the addresses too, and `neoaprs db get web/key` prints the key on a computer with no screen. Switching the network off closes the pages that came in by it; on a page opened from another device the page asks first ("This device will lose the page. Turn off?", Yes or Cancel). The alert of the command runs on this computer; the page alerts in the browser it is open in ("Messaging", "Alerts in the page").

* **What is refused.** The page's files are free (they hold the key screen), but the socket that carries the data and the base map answer `401` to a device that has not logged in. This computer is never asked for a key; a request that carries `X-Forwarded-For`, `Forwarded` or `X-Real-Ip` came through a proxy and counts as from the network, so a reverse proxy on the Pi gets the key screen too.
* **Wrong keys.** Five in a minute from one address shut that address out for five minutes, even for the right key; the log has every wrong key and the shutting out, and never the key.
* **A new key.** *New key* (it asks twice) makes another and logs every other device out: their open pages are closed and their sessions end at once; the device that pressed it stays in. A key you type yourself (`neoaprs db set web/key abcd-efgh-jkmn`, read when the daemon next starts) is the same.
* **The session** is a cookie (`neoaprs_session`, HttpOnly, SameSite=Strict) that holds an expiry, a random number and an HMAC of them under the key, not the key: the daemon stores nothing, a session survives a restart and ends with the key.
* **Plain HTTP.** The key is sent once, and the session cookie with every request, in the clear: use it on a network you trust, and reach the Pi from outside through a VPN, not by opening the port to the internet.
* **Windows** asks whether to let NeoAPRS through its firewall the first time the switch is on: allow it on private networks.
* Whoever is logged in can change every setting, the alert command (a shell line the computer runs) among them: the key is the only lock, so give it to your own devices only.

### Install as an app

The page can be installed, so that it opens in a window of its own with an icon, and, once opened, its shell opens even while the daemon is away (it then says "daemon offline" and connects when the daemon is back). A browser installs a page only from a *secure* address: `http://127.0.0.1:7303/` and `http://localhost:7303/` on the computer that runs NeoAPRS, or an `https://` address (a reverse proxy in front of the daemon, with its host name in `web/allowed_hosts`).

* **On the computer that runs NeoAPRS** (Chrome, Edge, Brave, Opera): open the page, then use the install icon at the end of the address bar, the browser's menu ("Install NeoAPRS…"), or **Install app** in the Settings tab, In this browser, which is there when the browser offers the install. Firefox and Safari on a computer do not install pages. The desktop app (`neoaprs app`) is a window of its own already.
* **From a Raspberry Pi over plain `http://`** the browser refuses the install and the worker, and the page works as before, with no message. A phone can still put it on the home screen as a shortcut: Android Chrome, menu, *Add to Home screen*; iPhone Safari, Share, *Add to Home Screen*. It opens in its own window with the NeoAPRS icon, and needs the daemon to be reachable, as the page does in a tab.
* **What the worker keeps.** The page's hashed files (`assets/`) are kept after their first use; the shell (`index.html`), the manifest, the icons, the symbol sheets and the glyph files are asked of the daemon every time, and a kept copy is shown only when the daemon cannot be reached, so an update is never hidden behind an old page and the page still loads itself again when the daemon says it was updated. The socket, the login, the base map and every request that is not a GET are never touched. A new release brings a new worker, which takes over at once and deletes the old files. To clear it: the browser's site settings, *Clear data* for the address.

### Update check

Once a day the daemon asks the project's version page whether a newer NeoAPRS is out, so that you hear of it and the project can tell how many copies are in use. The first question comes a minute after the daemon starts, then one every 24 hours; a desktop app and the daemon it starts count once, and opening the page asks nothing.

* **What is sent.** One GET of `update/url` with the version and the kind of system in the address: `https://oh2gba.eu/neoaprs/version.php?v=0.1.0&os=linux`, and a User-Agent that says the same (`NeoAPRS/0.1.0 (linux)`). The system is `windows`, `macos`, `linux`, `linux-appimage` (the AppImage) or `linux-arm` (a Raspberry Pi: aarch64 or armv7). Nothing else: no call, no position, no setting, no identifier.
* **What is kept.** The page adds a line with the time (to the minute, UTC), the version and the system to a log on the server and hands the same three values to the project's status page, where they are counted. No address of yours is stored: the address of the request is used only to tell two copies of the same version and system apart in the count, and is not stored anywhere. The source of the page is `server/version.php`.
* **The answer** is a few lines of JSON, the latest release of the project (read from its GitHub releases), the address of the project page and an optional note. When the version is newer than yours, the page shows it small in the footer under the panel after the version number, as a button that opens the steps to update ([Updating](#updating)); the note is its hover title. A page that cannot be reached, or answers something else, is ignored: nothing is shown, the log has a line only with `--debug`, and the next question is the next day.
* **Switching it off.** It is always on and has no setting. `NEOAPRS_UPDATE_CHECK=0` in the environment switches it off for one run (`CONVENTIONS.md`, the table of environment variables). `update/url` can point at a page of your own (`neoaprs db set update/url ADDRESS`; it is not on the page).
* **Check now.** The button of the Update check group (Settings tab) asks the version page at once, with the same request, and says beside it for a few seconds `up to date (0.3.0)`, `0.4.0 available` (a button that opens the steps to update; the header shows the version too) or why there was no answer. It works with the daily check switched off by the environment, since you pressed it, and does not move the daily schedule.

### Updating

When the update check finds a newer version, an **Update to 0.4.0** button appears in the footer under the panel, after the version (on a phone too, in full); a click opens a panel with a link to what is new (the release's notes on GitHub, in the page's link colour) and the steps for the way **this** copy was installed, the commands each with a copy button. The daemon works the kind out (`neoaprs/cli/installkind.py`) and tells the page in `hello`; the same steps are here. Your data (settings, messages, packets, the map) stays in every case.

| installed as | how to update |
|---|---|
| Windows installer | download `NeoAPRS-Setup-VERSION.exe` from the [release](https://github.com/oh2gba/neoaprs/releases/latest) and run it; it ends the running app and daemon, replaces the program and starts it again |
| AppImage | download `NeoAPRS-VERSION-x86_64.AppImage`, `chmod +x` it, quit NeoAPRS and start the new file. When a service starts the AppImage (the unit names the old file), run `./NeoAPRS-VERSION-x86_64.AppImage service install` once from where you keep the new file, so that the service starts it; then delete the old file |
| .deb (Raspberry Pi, Debian, Ubuntu) | download `neoaprs_VERSION_arm64.deb` (`_amd64.deb` on a PC) from the [release](https://github.com/oh2gba/neoaprs/releases/latest) and run `sudo apt install ./neoaprs_VERSION_arm64.deb`: it replaces `/opt/neoaprs` and restarts a running service; if the service still runs the old version, `systemctl --user restart neoaprs` |
| install line (`uv tool`) | run `curl -LsSf https://github.com/oh2gba/neoaprs/releases/latest/download/install.sh \| sh` again: it updates NeoAPRS and restarts the service |
| pip | `pip install -U neoaprs` (or `uv pip install -U neoaprs`) in its environment, then restart: `neoaprs service install` restarts a service, else quit NeoAPRS and start it again |
| a clone of the repository | `git pull`, `uv sync`, then `systemctl --user restart neoaprs` for a service, else quit and start it again |

**Open pages follow by themselves.** The page is built for one version of NeoAPRS (the number is built in) and the daemon says its version in `hello`: when they differ, the page loads itself again once, in a browser tab and in the desktop app's window alike, and has the new one; the daemon serves the page's `index.html` with `no-cache` and the other files by the hash of their content. It loads again for the next update too (the page remembers only which version it loaded for, and forgets it when the versions agree again); a daemon that serves a page older than itself does not make it loop.

### The desktop app

`neoaprs app` (or `neoaprs-app`, the same without a console window) is NeoAPRS for people who do not want to run a daemon: the page in a window of its own and an icon in the tray. It needs the extra `app`: `uv tool install "neoaprs[app]"` or `pip install "neoaprs[app]"` (in a clone `uv sync --frozen --extra app`); the Windows installer has it inside. The window is the page, not a second program: the same page that the daemon serves, in the system's own web engine, so anything the page does in a browser it does here.

* **Attach or start.** With a daemon holding the data folder's lock (a service, `neoaprs run` in a terminal, `neoaprs open`) the app attaches: it reads the page's address from the log, as `neoaprs open` does, and shows it; **Quit leaves that daemon running**, and a systemd user service keeps running. With none, the app starts one, detached, by the code of `neoaprs open`, and owns it: **Stop and quit** stops it (the same end as `neoaprs stop`: `NeoAPRS ended` in the log) and, while it runs, the app notices when something else stops it (`neoaprs stop`, the uninstaller, the Start menu's Stop NeoAPRS) and ends too. The daemon outlives a crash of the window, and a crashed app leaves a daemon that the next `neoaprs app` attaches to.
* **The window.** Titled NeoAPRS, 1280x800 the first time, then the size it was closed with (`neoaprs-app.json` in the data folder). What the page keeps in the browser (the panel's width and tab, the map's view, the messages and bulletins seen) is kept in the folder `webview/` of the data folder, so it survives a restart; it belongs to the page's address, `127.0.0.1` and the port, so a page that moves to another port (the 7303 was taken) starts with a clean slate there. Closing the window **hides** it; NeoAPRS goes on listening in the tray. A link to another site (the QRZ page of a call, the credits of the map) and a link with `target="_blank"` open in the system's browser and never in the window; `file:` and `javascript:` addresses are dropped (`neoaprs/desktop/links.py`).
* **The tray menu.** *Open NeoAPRS* (also the click on the icon) shows the window; *Open in browser* shows the page in the browser; *Start at sign-in* is a checkbox; *Stop and quit* stops the daemon if the app started it and ends the app. For an attached daemon the last item reads *Quit (NeoAPRS keeps running as a service)* and only ends the app.
* **Start at sign-in** makes the app, in the tray with the window hidden, start when you sign in: `neoaprs-app --tray`. On Windows it is the value `NeoAPRS` of the Run key, the same entry the installer's task and `neoaprs service install` write (so there is one start at sign-in, and the checkbox replaces a daemon entry from `neoaprs service install` with the app's); on Linux an XDG autostart file, `~/.config/autostart/neoaprs.desktop` (`$XDG_CONFIG_HOME`), which KDE, GNOME and the others read; macOS has none and the item is not there. The daemon is not a second thing to start: the app starts it.
* **One app.** A second `neoaprs-app` on the same data folder raises the first one's window and ends (with `--tray` it only ends): the first holds the lock `neoaprs-app.lock` and listens on a loopback port that it writes into `neoaprs-app.port`, and the second says `show` there. `neoaprs app --quit` says `quit` the same way and waits until the app has ended; the Windows uninstaller and an update use it. The daemon's own lock, `neoaprs.lock`, is the one the daemon holds; the two do not meet.
* **Alerts are the daemon's.** The tray shows no toast of its own: the daemon's alert command (`messages/alert`, "Messaging", "Alerts"), whose default shows a notification on both systems, runs whether the app is open, hidden in the tray or not installed at all, and is configured and tried in one place, the Settings tab. The toolkits' notifications (`QSystemTrayIcon.showMessage`, pystray's `notify`) are used only to say why Start at sign-in could not be changed.
* **When there is no window.** The app chooses what the computer can run and says what it chose, and why, in `neoaprs-app.log`: the window and the tray; without the web engine (or, on Windows, without the WebView2 runtime, which Windows 11 and every current Windows 10 have; pywebview would otherwise fall back to the old Internet Explorer engine, which cannot show the page) the tray and the page in the browser (*Open NeoAPRS* is the browser then); without any toolkit the page in the browser and nothing else, the daemon left running and the way to end it (`neoaprs stop`) printed. A window that cannot start at all (no display) is the same fallback and exit code 1. A desktop with no system tray (GNOME without its extension) gets the window, and closing it quits, there being nothing to bring it back from; at sign-in the tray is waited for for a minute, since the panel may start after the app.
* **Which toolkit.** Linux and macOS: Qt, `PySide6-Essentials`, `PySide6-Addons` and `PySide6-WebEngine` (the web engine is its own wheel that needs the other two; about 260 MB to download and 670 MB installed on Linux, which is Qt WebEngine, a Chromium): `QWebEngineView` is the window and `QSystemTrayIcon` the tray, one event loop (`neoaprs/desktop/qtshell.py`, `qtwindow.py`). Windows: `pywebview` (WebView2, the Edge engine that is already on the computer) for the window and `pystray` with `Pillow` for the tray icon (`winshell.py`): about 9 MB of wheels, and the frozen app carries no browser. The two are not one library because pywebview's Qt backend would need the tray from a library that does not share Qt's event loop on Linux, while Qt has both.
* **Files in the data folder:** `neoaprs-app.log` (the app's log, rotating, 1 MB), `neoaprs-app.json` (the window's size), `neoaprs-app.lock` and `neoaprs-app.port` (the one-app rule), `webview/` (the web engine's storage). The icon is `neoaprs/desktop/icon.png` (the tray) and `icon.ico` (the Windows programs), made by `scripts/make-icon.py`.
* **Windows.** The installer (below) gives the Start menu's *NeoAPRS* the app, an optional desktop shortcut, the task *Start NeoAPRS when I sign in* the app in the tray, and "Open NeoAPRS now" the app. The app is `neoaprs-app.exe` (not NeoAPRS.exe: Windows file names ignore case, and that would be `neoaprs.exe`, the console program).
* **Tests.** The logic runs with no toolkit (fakes of the window and the tray; `tests/README.md`), the Windows shell against stand-ins for pywebview, pystray and Pillow, the Qt shell headless with the real PySide6 (`QT_QPA_PLATFORM=offscreen`, skipped without the extra); a real tray, real Wayland or X11 windows and a real WebView2 are what only a desktop can try.


### The AppImage

`NeoAPRS-VERSION-x86_64.AppImage` is the Linux download: one file with CPython 3.13, NeoAPRS and the desktop app's Qt web engine inside (about 150 MB), for any x86_64 Linux with glibc 2.34 or newer (Ubuntu 22.04, Debian 12, Fedora 35 and newer; the Qt wheels set the limit) and the usual desktop libraries; nothing is installed. Make it executable and run it:

```bash
chmod +x NeoAPRS-0.1.0-x86_64.AppImage
./NeoAPRS-0.1.0-x86_64.AppImage                     # no arguments: the desktop app (neoaprs-app)
./NeoAPRS-0.1.0-x86_64.AppImage doctor              # arguments: the neoaprs command (--version, open, stop, service install, map, ...)
```

* **Data** is where every install keeps it, `~/.local/share/neoaprs` (`$XDG_DATA_HOME/neoaprs`): a newer AppImage in place of the old one finds its settings, messages and map, and the file can be deleted without touching them. The pmtiles tool for the map is fetched into its `bin/` the first time the map is made.
* **The radio's port** needs the group that owns serial devices, as everywhere on Linux: `sudo usermod -aG dialout $USER` (`uucp` on Arch), then log out and in; `./NeoAPRS-0.1.0-x86_64.AppImage doctor` says so.
* **FUSE.** The file mounts itself with `fusermount`, which the `fuse3` (or `fuse`) package provides; the runtime is static, so `libfuse2` is not needed. Without FUSE (a container, a minimal install) run it with `--appimage-extract-and-run` as the first argument, which unpacks it into a temporary folder at every start, or `--appimage-extract` once and run `squashfs-root/AppRun`.
* **Start at login.** `./NeoAPRS-0.1.0-x86_64.AppImage service install` writes the systemd user unit with the AppImage file as `ExecStart` (the folder the file is mounted at is gone when it ends, so the unit never names it), and the tray menu's *Start at sign-in* writes the same file into the autostart entry. Move the file first, then run the command again from its new place; after an update run it from the new file.
* **The window.** The web engine's sandbox needs user namespaces; where the system refuses them (the AppArmor of Ubuntu 24.04) `AppRun` starts the engine without it, which is safe here since the window shows only NeoAPRS's own page.
* **Built** by `scripts/build-appimage` from the wheel: the relocatable CPython of python-build-standalone, the locked dependencies of the extra `app` (`uv export`), the wheel, and appimagetool with its static runtime, each tool pinned by version and SHA-256 at the top of the script; `packaging/appimage/prune.py` takes out what is not run (tests and Tk of CPython, Qt but the web engine and the modules the app imports), `AppRun` and `neoaprs.desktop` are beside it. `scripts/smoke-appimage FILE` is the test of the file ("Releases" below).

```bash
scripts/check               # every stage of the table below: the one gate
scripts/check --stage mypy  # one stage
.venv/bin/pytest -q tests/test_store.py
```

Dependencies are in `pyproject.toml` and `uv.lock` only: tornado, pydantic and pyserial at run time, and the extra `app` for the desktop app (pywebview, pystray and Pillow on Windows, PySide6 with its web engine elsewhere; `uv sync --frozen --extra app` in a clone, which CI does, and a plain `uv sync` takes them out again; the tests of the Qt shell are skipped without them) (the build backend is hatchling; `uv build` makes the sdist and the wheel, about 1.3 MB with the page in it, and `tests/test_package.py` installs the wheel into a fresh venv and runs `neoaprs --version`, `neoaprs doctor` and the daemon from it); pytest, pytest-asyncio, pytest-xdist, mypy, ruff, hypothesis and coverage for development. `scripts/check` is the gate: the stages are the ones in the table below.

### Continuous integration and the smoke test

`.github/workflows/ci.yml` runs on every push to `master` and to a `ci/**` branch, and on every pull request. Its jobs:

| job | where | what |
|---|---|---|
| `python` | Linux and Windows (`ubuntu-latest`, `windows-latest`), Python 3.13 | the system libraries of the Qt web engine (Linux), `uv sync --frozen --extra app`, `uv lock --check`, `ruff`, `mypy`, `pytest -n auto`; on Linux also `mypy --platform win32`, so that one tree type-checks for both systems |
| `smoke` | Linux and Windows | `uv build --wheel`, the wheel installed into a fresh venv, then `scripts/smoke.py --command <venv>/bin/neoaprs` (`Scripts\neoaprs.exe`) |
| `page` | Linux | the page's type check, lint and tests, and the committed `neoaprs/page/` is what `ui/` builds |

`.github/workflows/release.yml` is the other workflow: on a tag, the release ("Releases" below).

What only makes sense on a POSIX system is marked `posix_only` (`tests/support/ptyline.py`) and skipped on Windows: pseudo-terminals and device files, `/proc`, file modes, shell scripts and the stand-ins that are shell scripts (the fake `systemctl`, the fake `pmtiles`), the checks of the repository itself (documents, scripts, the unit files) and the ones that need `git` and `bash`. Everything else runs on both systems; `tests/README.md` has the details. The daemon, when a test starts it as a process, is stopped on Windows with Ctrl+Break in a process group of its own (`tests/support/proc.py`): `terminate()` there is a kill.

`scripts/smoke.py` is the same check an installer or a package must pass. It starts a fake KISS TNC on a free TCP port (it plays `tests/fixtures/kiss/thd7-2026-10-21.bin`), starts the daemon on a temporary data folder with `--port socket://127.0.0.1:PORT --web-port 0`, reads the page's port from the log line `web page at`, fetches `/` (200, `<div id="app"`, the Content-Security-Policy header) and the first script under `/assets/`, opens `/ws` and waits for the TNC to be `connected` and for a packet, then stops the daemon (SIGTERM; Ctrl+Break on Windows) and checks exit code 0, `NeoAPRS ended` as the last line of the log and `PRAGMA integrity_check` on the database. Run it against a clone with `.venv/bin/python scripts/smoke.py`, or against an installed command with `--command PATH` (and the Python that has NeoAPRS installed: it uses Tornado's WebSocket client). It prints what it checks and exits 0, or says the first thing that was wrong with the end of the daemon's log and exits 1.

### The .deb

`neoaprs_VERSION_arm64.deb` for a Raspberry Pi (64-bit Raspberry Pi OS) and `neoaprs_VERSION_amd64.deb` for a PC with Debian or Ubuntu are the install for a machine without a screen. NeoAPRS needs Python 3.13, which Raspberry Pi OS and Debian 12 do not have, so the package brings its own CPython (python-build-standalone) and the locked dependencies, without the desktop app's Qt (about 20 MB to download, 60 to 70 MB installed), and uses nothing of the system's Python; it depends on libc and libgcc only. Debian 12, Ubuntu 22.04 and Raspberry Pi OS (Bookworm) and newer are meant; the CI installs it on the current Ubuntu of each architecture.

```bash
sudo apt install ./neoaprs_0.4.0_arm64.deb          # apt, not dpkg -i: it checks the package, and the file must start with ./
neoaprs service install --linger                    # as your own user, not root: starts it at boot and keeps it running
neoaprs doctor                                      # what is wrong with this computer, if anything
```

* **What is installed.** Everything in `/opt/neoaprs` (the Python, its libraries, NeoAPRS; a Python of its own, started with `-I`, so that your `PYTHONPATH` and user site are not mixed in), `/usr/bin/neoaprs` (a link to the command `/opt/neoaprs/bin/neoaprs`) and `/usr/share/doc/neoaprs` (the copyright file with the GPL-3.0-or-later, the manual, the README and the changelog). No manual page and no service of the system.
* **The service is the user's.** The package writes nothing in anyone's home and starts nothing at install; the service is made by the command above, as the user who is to run NeoAPRS (`neoaprs service install`, "As a service": a systemd user unit that starts `/opt/neoaprs/bin/python3 -m neoaprs`, which an upgrade does not move). The install says so when it finishes, with the `usermod -aG dialout $USER` line for the serial port that `neoaprs doctor` also gives.
* **Upgrading.** `sudo apt install ./neoaprs_NEW.deb` replaces the files of `/opt/neoaprs`. The installation then restarts the NeoAPRS service of each logged-in user who has one running (`systemctl --user --machine=UID@.host restart neoaprs`, which writes nothing in their homes); when that cannot be done (no systemd, an older systemd, a daemon started by hand) it says that a running NeoAPRS keeps the old version until it is restarted: `systemctl --user restart neoaprs`. The page of the running daemon follows by itself ("Updating"). The update panel of the page gives these steps with the download for the machine's architecture.
* **Removing.** `sudo apt remove neoaprs` takes `/opt/neoaprs`, the link and the documents away and leaves your data (`~/.local/share/neoaprs`) and the unit in your home, which can no longer start: `neoaprs service remove` before removing the package takes the unit away, or afterwards `systemctl --user disable --now neoaprs && rm ~/.config/systemd/user/neoaprs.service`.
* **Built** by `scripts/build-deb` from the wheel: the CPython of python-build-standalone for the architecture (pinned by version and SHA-256 in the script), the locked dependencies as wheels for that platform (`uv pip install --python-platform`, so either architecture is made on either kind of machine), the wheel, the files `packaging/deb/` holds (`control.in`, `postinst`, `postrm`, `copyright`, the `neoaprs` command), `packaging/appimage/prune.py --python-only` for what is not run, the bytecode of everything compiled in advance, and `dpkg-deb`. No debhelper. The result is the same bytes each time for the same inputs (`SOURCE_DATE_EPOCH` is the last commit's time unless set).

### Releases

What a release holds, on https://github.com/oh2gba/neoaprs/releases: `NeoAPRS-Setup-VERSION.exe` (the Windows installer), `NeoAPRS-VERSION-x86_64.AppImage` (the Linux app, "The AppImage" above), `neoaprs_VERSION_arm64.deb` and `neoaprs_VERSION_amd64.deb` ("The .deb" above), `neoaprs-VERSION-py3-none-any.whl` and `neoaprs-VERSION.tar.gz` (the wheel and the sdist), `install.sh` (Linux and macOS) and `SHA256SUMS`, with build provenance attached to each file (`gh attestation verify FILE --repo oh2gba/neoaprs`). `.github/workflows/release.yml` makes all of it when a tag `v*` is pushed, and nothing is built by hand. Its jobs:

| job | where | what |
|---|---|---|

| `wheel` | Linux | `uv build` (the sdist, and the wheel built from it); the wheel is installed into a fresh environment and `scripts/smoke.py` runs against it |

Started by hand (Actions, release, *Run workflow*, or `gh workflow run release.yml --ref BRANCH`) it is a dry run: the same builds and checks on that branch, `verify` and `release` skipped, and the files kept for a few days as the artifacts of the run (`gh run download RUN_ID`).

**To make a release:** (1) set `VERSION` in `neoaprs/__init__.py`; (2) turn `## Unreleased` of `CHANGELOG.md` into `## VERSION` (the notes of the release are that section) and add a fresh `## Unreleased` above it; (3) `scripts/check`, commit, push `master` and wait for CI; (4) `git tag vVERSION && git push origin vVERSION`; (5) watch the run (`gh run watch`), then open the release and read the notes. A tag whose number is not `VERSION` stops at `verify`; a failed job leaves no release. Nothing signs the installer: Windows SmartScreen says "Windows protected your PC" for an unsigned file the first times (**More info**, **Run anyway**), which the README says.

**The Windows installer.** Per user, no administrator rights and no UAC prompt: the app goes to `%LOCALAPPDATA%\Programs\NeoAPRS`. The Start menu group *NeoAPRS* has **NeoAPRS** (`neoaprs-app.exe`: the desktop app, which starts the daemon if none runs) and **Stop NeoAPRS** (`neoaprsw.exe stop`), and the uninstaller. The task **Desktop shortcut** (off by default) adds NeoAPRS to the desktop. The task **Start NeoAPRS when I sign in** is on by default and sets the value `NeoAPRS` of the Run key of the user to `neoaprs-app.exe --tray` (the app in the tray; the daemon is the app's to start); the last page offers **Open NeoAPRS now**, which runs the app. Installing over an older version ends the running app and daemon first (`neoaprs-app.exe --quit`, `neoaprs.exe stop`). The uninstaller runs `neoaprs-app.exe --quit`, `neoaprs.exe stop` and `neoaprs.exe service remove` and removes the program folder; the data folder `%LOCALAPPDATA%\NeoAPRS` (settings, messages, packets, the map) is never touched. Silent: `NeoAPRS-Setup-VERSION.exe /VERYSILENT /SUPPRESSMSGBOXES /CURRENTUSER` (`/TASKS=""` for no start at sign-in and no desktop shortcut, `/DIR=` for another folder, `/LOG=FILE`).

**The install script.** `curl -LsSf https://github.com/oh2gba/neoaprs/releases/latest/download/install.sh | sh` on Linux and macOS: installs uv with Astral's installer when there is none, `uv tool install --force --python 3.13` of the release's wheel, `neoaprs service install` (a systemd user unit; launchd on macOS), a restart of the service when it was an update, the `usermod` line for `dialout` (`uucp`) when you are not in the group, the page's address and `neoaprs doctor`. It needs no root. `NEOAPRS_WHEEL_URL` (`CONVENTIONS.md`) takes another wheel address, which is how the workflow tests it.

### The page on a phone, a tablet and a desktop

**One box to write in.** On the tabs Messages, Bulletins, Email and Objects the list or the board fills the tab and scrolls, and the box to write in is fixed at the bottom of it: the fields, and under them one line with the counter ("67 left") and the buttons at the right, the secondary one (Cancel) left of the primary one (Send, Post, Save), which is the last. On a phone the box stays above the home bar and the page is as high as the window that is left (`100dvh`), and the field being typed in is scrolled into view when the keyboard comes up; the form of an object scrolls inside the box on a short screen, its buttons always in sight. A list of suggestions or the note of an (i) in the box opens upward (`ui/src/components/ComposeBar.vue`).

The page chooses its layout from the size of the window (`lib/layout.ts`, `composables/useViewport.ts`; the root of the page carries `size-phone`, `size-tablet` or `size-desktop`, and `style.css` and `responsive.css` go by that class, not by media queries of their own, so that the script and the style never disagree).

| size | window | what it looks like |
|---|---|---|
| **phone** | under 700 px wide, or shorter than 500 px and under 1000 px wide (a phone held sideways) | one view at a time. A compact header, the tab bar under it (the tabs as one **☰** button when they do not fit), and the rest of the screen is the open tab with the footer under it, or the map. The first button of the tab bar is **Map**: it shows the map on the whole screen, and a tab of the bar brings its tab back (the view is remembered). A station's card is a bottom sheet, part of the screen: folded to its head and the first facts, a tap or a swipe up on its grip opens it, a swipe down folds it and a swipe down on the folded sheet closes it; it has its close button too (held sideways it is a sheet at the left). A tap on a row of the Stations tab shows the map with the card; **Message** and **Edit** on the card and the mail count of the header bring the tab (the radio message of the footer is under a tab already). **Pick on the map** (Beacon, Objects) shows the map with a bar ("Tap the place on the map", **Cancel**), and the tab comes back with the place filled in. The setup guide is the whole screen (its **Pick on the map** folds it to its head, over the map). One card at a time: a tap replaces it. |
| **tablet** | 700 to 1100 px | the map and the panel side by side, the panel 380 to 420 px wide (40 % of the window between those; there is no handle: a finger cannot drag it), with the fold button. Up to four cards side by side, as many as the width of the map has room for. |

The Stations table is one block at most 640 px wide, in the middle of a wider panel; the filter box and its three tickboxes wrap onto a second line when they do not fit.

On every size the page is the height of the window (`100dvh`: it follows the toolbars of a phone), does not scroll sideways, keeps clear of the notch and the home bar (`viewport-fit=cover`, `env(safe-area-inset-*)`), and on a touch screen (`pointer: coarse`) every button, tab, field and row is at least 40 px high and a field has a 16 px font, so that a phone does not zoom the page in when one is focused. The installed app (`display: standalone`) uses the same layout.

**Several station cards.** A click on a marker or on a row of the Stations table opens that station's card and closes the others. With **Ctrl** held (**Cmd** on a Mac) the click adds the card to the open ones, or closes it when it is open already; this is for comparing, for instance several weather stations. The cards are side by side in a row over the map, from its left, the oldest at the left and the newest at the right. **Every card is the whole card**, the same as when it is alone, and a weather station's has its graphs: opening more cards makes none of them smaller. While two or more weather cards are open each graph is on the same value axis and the same time span on all of them, so that the stations can be compared at a glance; a single card keeps its own axis. When the row is wider than the map has room for the oldest card closes (a card is never made narrower): on a desktop up to four, on a tablet up to two, on a phone one (a tap replaces it). Each card has its own cross; with two or more open, **Close all** and **Message these 3** are at the top left of the map beside the zoom buttons (the count is of the open cards that are stations that can be messaged, not ourselves; the second button is there from two, and opens the Messages tab with the group compose for those stations). The marker and the row of every open card have the selected look, the track of every open card is highlighted and the route to our station is drawn for the newest card only. A card added from the table does not fly the map to the station (a plain click does). A station past its timeout stays in the table (listed last, "timed out") and a click on it, with Ctrl or without, shows its marker and track on the map for as long as its card is open. **Esc** closes all the cards at once and clears the selection (not while a field has text in it: in the filter box of the Stations table the first Esc clears the text and the next closes the cards; and not while the setup guide or the update panel is open: they take the key).

* **The source** is `ui/`: Vue 3, TypeScript strict, Vite, vitest, eslint (no warnings), prettier, knip and jscpd, versions pinned in `ui/package.json` and `ui/package-lock.json`. `src/lib` is logic without Vue (the socket client `hub.ts`, the symbol sprites, the sorting of the table, the map style), `src/composables` state and behaviour (`useDaemon` holds the ten topics as reactive maps, reconnects with a backoff and shows "Daemon offline" in the footer; `usePanel`, `useSelection`, `useMessagesView`, `useEmail`, `useBulletins` and `useOwnObjects` are the panel, the station picked, the Messages tab, the Email tab, the Bulletins tab and the Objects tab as the page runs them, so that `App.vue` is the shell that hands them to the components), `src/components` the single-file components (none over 300 lines; they take props and emit events). Every type of the wire comes from `ui/src/protocol/`, which `scripts/gen-protocol.py` writes: there is no hand-written copy of a row.
* **How it is built:** `scripts/build-page` does `vue-tsc` and `vite build` (after `npm ci` when `ui/node_modules` is not current) into a temporary folder and renames it to `neoaprs/page/` (the environment variable `NEOAPRS_OUT` of `CONVENTIONS.md` says where Vite writes; the script points it at the temporary folder). `neoaprs/page/` is committed, so the machine that runs NeoAPRS needs no node. Beside the page it has the manifest and the icons (`ui/public/manifest.webmanifest`, `ui/public/icons/`, made from `site/favicon.svg`) and the service worker `sw.js`, which `vite.config.ts` writes from `ui/sw/sw.js` with the version of the package in it ("Install as an app"); the daemon serves them with `Cache-Control: no-cache`, the manifest as `application/manifest+json`. `cd ui && npm run dev` serves the source with hot reload on port 5173 and proxies `/ws`, `/basemap.pmtiles` and `/basemap-world.pmtiles` to a daemon on port 7303.
* **The gates** are the stages `ui-types`, `ui-lint`, `ui-tests`, `ui-build`, `page` and `dup` of `scripts/check`; `page` fails (`tests/test_page_build.py`) when `neoaprs/page/` is not what `ui/` builds, so a change to `ui/` is not done until `scripts/build-page` has run and `neoaprs/page/` is committed with it. The same test holds the page to the Content-Security-Policy of `neoaprs/web/headers.py`: no inline script, no eval, and MapLibre's worker is a file of `neoaprs/page/assets` (it would make one from a blob otherwise, which the policy forbids).
* **The base map** is two files of the data folder that the daemon serves with byte ranges: `basemap.pmtiles`, the OpenStreetMap map of the area round the station (a square of `map/radius_km` in every direction, down to `map/maxzoom`, 12 unless `neoaprs db set` changed it), and `basemap-world.pmtiles`, the world to zoom 5 (about 15 MB) that the page draws under it, so that there is something to see outside the area and when zoomed out. The daemon makes them itself, from the Settings tab, Map, which has the **Radius** and one button, **Download map** ("Download map again" when there is a detailed map, with one plain line "Map downloaded 23 Oct" beside it; the world map ships with NeoAPRS and is not mentioned, the details are in the log). The first press runs the estimate itself (the `map_estimate` dry run, "Checking size…") and the button then asks "Download 493 MB?" with the real size, always; the second press makes the world map (if there is none) and then the detailed map, with the percent of the step shown as a bar and the size downloaded so far beside it ("Map of the area 49% · 340 MB"), and **Cancel** ends the job (the half-made file is removed and the map that was there stays). A change of the radius takes the question back. One job runs at a time, and the button waits for a change of the radius that is being saved and for the station to have a position. The estimate and the download use the stored `map/maxzoom` and `map/source`, so an expert's own source or detail still works. The files are cut with the `pmtiles` program of [go-pmtiles](https://github.com/protomaps/go-pmtiles) (BSD-3-Clause) out of the daily build of build.protomaps.com (`map/source`), each into a `.part` file that is moved into place when the program has finished. The program is run with `--download-threads=8` (eight requests at a time; its own default is four). A download that stands still, with neither the percent nor the size of the `.part` file moving for 2 minutes, is ended and begun again from the start (the program cannot take up a half-made file), after a pause of 10 seconds, three times in all, and the page says so ("no progress: trying again (2 of 3)"); when the last try stands still too the job ends with "the map server is too slow now; try again later", and the map that was there stays. The program is the one on the PATH, else `bin/pmtiles` (`bin/pmtiles.exe` on Windows) in the data folder; when there is neither, the release for this system (Linux and macOS on x86_64 and arm64, Windows on x86_64) is downloaded from GitHub into `bin/`, and only if its SHA-256 is the one written in `neoaprs/pmtilestool.py` (the pin is the trust: a new version of the tool is a change of that table). The same is `neoaprs map` on the command line (`scripts/fetch-basemap` in a clone). By hand: put `pmtiles` on the PATH and run `pmtiles extract https://build.protomaps.com/YYYYMMDD.pmtiles data/basemap.pmtiles --bbox=WEST,SOUTH,EAST,NORTH --maxzoom=12` (and the same with `--maxzoom=5` and no `--bbox` into `data/basemap-world.pmtiles`); a file made that way is shown all the same, its area and zoom read from its header. Without either file the map area says "No base map" with a Download button over a blank background and the stations are drawn all the same. The names of places and roads are drawn with the glyph files in `ui/public/fonts/` (Noto Sans Regular and Medium, made by the Protomaps `basemaps-assets` project, SIL Open Font License 1.1: `OFL.txt` is beside them).
* **The symbols** are the aprs.fi high-resolution symbol set by Heikki Hannikainen, OH7LZB (<https://github.com/hessu/aprs-symbols/>): the three sprite sheets (primary, alternate, overlay characters; 48 px a symbol) are in `ui/public/symbols/`, unchanged. The repository has no licence file; its README says the set is released to the APRS community for use by any APRS application, for free, and asks that a user gives a pointer to the source, which is done here, in the (i) on the map, and in `ui/public/symbols/SOURCE.txt`; its COPYRIGHT.md, which says where each symbol comes from and under what terms (many public domain or CC BY-SA, the old APRS set's originals without licence information, three company logos), is kept beside the sheets as `COPYRIGHT.txt`. If that is not good enough for a wider distribution, replace the three sheets and `src/lib/symbols.ts` is the one file that knows their layout.
* **The credits** shown in the (i) on the map: "© OpenStreetMap contributors, Protomaps" (the base map data is OpenStreetMap's, ODbL, in the Protomaps tile format) and the symbol set above. MapLibre GL JS (BSD-3-Clause) and PMTiles (BSD-3-Clause) are in the build.

## What is in the folder

* `neoaprs/`: the daemon (the layers are in `docs/ARCHITECTURE.md`): `clock`, `signal`, the protocol (`kiss`, `ax25`, `callsign`, `geo`, `symbols`, the `aprs*` decoders with `aprsthirdparty` and `aprsweather`, `packet`, `packetcodec`, `route`); `message`, `pref`, `tncmode`; `config`, `stationbook`; `source`, `tasks`, `serialport` with `serialholders` and `serialprobe`, `tnc` with `tncsearch` and `tncwatchdog`; `bulletin`; `services/beacon`, `services/messaging` with `services/inbox` and `services/heard`, `services/bulletins`, `services/queries`, `services/prefbook`; the database actor (`db`, `dbthread`, `dbfile`, `dberror`, `dbstats`, `dbopen`, `durable`, `walcare`, `backupfolder`), `migrations`, `store`, `storesql`, `dblog`, `packetsql`, `packetlog`, `messagesql`, `messagelog`, `bulletinsql`, `bulletinlog`, `weathersql`, `weatherlog`, `paths`; `app`, `wiring`, `controller`, `daemon` (the process), `__main__` (`python -m neoaprs`), and the packages `cli/` (the `neoaprs` command: `service`, `doctor`, `db`, `map`, `replay`, `capture`, `open`, `stop`), `desktop/` (the desktop app: "The desktop app"), `web/` and `page/` (below).
* `tests/`: the suite (`tests/README.md`); `tests/support/` is what the tests are built from, `tests/safety/` the tests of the database actor, `tests/fixtures/` the captured frames and streams of the radio and the parser's cases.
* `scripts/`: the tools (table above).
* `.github/`: the CI workflow (`.github/workflows/ci.yml`: the Python checks and tests, the smoke test, the page's checks, a stale-page check), run by GitHub on every push, and the release workflow (`.github/workflows/release.yml`), and the workflow of the project page (`.github/workflows/pages.yml`).
* `site/`: the project page ("The project page").
* `server/`: the version page that the update check asks, on the project's web host: `version.php`, `log/.htaccess` (the log and the cache are not served), `deploy.sh` (uploads those two files and nothing else) and `usage-report.sh` (fetches the logs and counts the starts per day, version and system). `docs/MAINTAINING.md` has when to look at it.
* `packaging/`: what the release is made from besides the package: `install.sh.in` (the install script's template) and `test-install.sh` (its test), and `windows/` (`neoaprs.spec` for PyInstaller with its entry script, `bundle_pmtiles.py`, `neoaprs.iss` for Inno Setup) and `appimage/` (`AppRun`, `neoaprs.desktop`, `prune.py`). "Releases".
* `.gitattributes`: LF line ends in every checkout (a Windows checkout would otherwise break the tests), the binary files marked.
* `systemd/`: the notes on the unit (`systemd/README.md`); the unit itself is the template `neoaprs/cli/neoaprs.service`.
* `docs/`: `docs/README.md` indexes every document; `docs/MANUAL.md` is this manual; `docs/ARCHITECTURE.md` is the architecture; `docs/screenshots/` holds the pictures of the front page.
* `LICENSE`: the GNU General Public License, version 3 (`pyproject.toml` says `GPL-3.0-or-later`).
* `data/` (not in git): the live data folder of a run from this folder.
* `neoaprs/web/` (a package of `neoaprs/`): the web server (Tornado) and the wire format of the page (pydantic models in `neoaprs/web/*wire.py`, the unions in `neoaprs/web/protocol.py`); `PROTOCOL.md` is generated from them.
* `ui/` and `neoaprs/page/`: the Vue 3 source of the page and its committed build, which is package data of the wheel (`ui/src/protocol/` is generated from `neoaprs/web/protocol.py`); "The page" below.
